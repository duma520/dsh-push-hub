## 一、Telegram

### 协议

```
POST https://api.telegram.org/bot<botToken>/sendMessage
Content-Type: application/json

{
  "chat_id": 6317114992,
  "text": "正文",
  "disable_web_page_preview": true
}

成功判定：返回 JSON 的 ok 字段为 true。
```

### 实测（2026-11-15）

| 项目 | 值 |
|---|---|
| bot id | 8639331459 |
| username | dumafu_dsh_bot |
| 目标 chat_id | 6317114992（用户 duma135） |
| 代理 | http://***已脱敏***-内网IP:20808（nekobox） |
| 直连 | **必然超时**，不可用 |
| 经代理 | sendMessage 返回 message_id=13，1–2 秒到达 |
| 单条上限 | 4096 字符 |

### 坑

1. **不配 proxy 会卡 25 秒然后失败。** 这台机器到 api.telegram.org 直连不通。
2. chat_id 必须是数字。如果你用的是 @channelname 形式，需要先 getUpdates 拿到真实 chat_id。
3. 频控：同 chat 每秒 1 条、每分钟 20 条。本库按块间隔 1.5 秒发，正常够用。

## 二、飞书（Feishu / Lark）

### 协议（两步）

第 1 步取 tenant_access_token：

```
POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal
{ "app_id": "cli_xxx", "app_secret": "xxx" }
→ { "code": 0, "tenant_access_token": "t-xxx", "expire": 7200 }
```

第 2 步发消息：

```
POST https://open.feishu.cn/open-apis/im/v1/messages?receive_id_type=open_id
Authorization: Bearer <tenant_access_token>
{
  "receive_id": "ou_xxx",
  "msg_type": "text",
  "content": "{\u005c"text\u005c":\u005c"正文\u005c"}"
}
→ { "code": 0, "data": { "chat_id": "oc_xxx" } }
```

注意 content 是**字符串**，里面再套一层 JSON。这是飞书最容易写错的地方。

### 实测（2026-11-15）

| 项目 | 值 |
|---|---|
| appId | cli_aa53bd0b3a… |
| domain | feishu（国内版） |
| 目标 peer | ou_20e30b127c39c90700e51d36980a8e77 |
| 发送结果 | code:0，chat_id=oc_7e10603a5843dcd27264b00612aea806 |
| 延迟 | 1–2 秒 |
| 单条上限 | 约 2000 字符 |

### 坑

1. **域名分国内/海外。** domain=larksuite 时要用 open.larksuite.com，用错会报 404 或 code 非 0。
2. **receive_id_type 三选一**：open_id、user_id、chat_id。本库判断规则：peer 以 oc_ 开头就用 chat_id，否则 open_id。
3. tenant_access_token 有效期 7200 秒，本库**每次发送都重新取**（省去缓存失效判断，代价是多一次 HTTP）。
4. code 99991663 = token 无效；99991664 = 权限不足。

## 三、QQ（QQ 开放平台）

### 协议（两步）

第 1 步取 access_token：

```
POST https://bots.qq.com/app/getAppAccessToken
{ "appId": "1905799217", "clientSecret": "xxx" }
→ { "access_token": "xxx", "expires_in": 7200 }
```

注意 **appId 必须是字符串**，传数字会报参数错误。

第 2 步发单聊消息：

```
POST https://api.sgroup.qq.com/v2/users/<openid>/messages
Authorization: QQBot <access_token>
{ "content": "正文", "msg_type": 0 }
→ 200 带 { "id": "ROBOT1.0_xxx", "timestamp": ... }
```

### 最大的坑：授权头是 QQBot，不是 Bearer

写 Authorization: Bearer <token> 会返回 **401 Unauthorized**。正确格式是：

```
Authorization: QQBot xxxxxxxx
```

注意中间是一个空格，且大小写敏感。

### 实测（2026-11-15）

| 项目 | 值 |
|---|---|
| 账号名 | 14386306 |
| appId | 1905799217 |
| 目标 openid | 6610BC7587D119042A0060CF987BDAEE |
| 发送结果 | 200，id=ROBOT1.0_… |
| 延迟 | 1–2 秒 |
| 单条上限 | 本库按 1800 字符切块（留余量） |

### 其它

- QQ 有 7 个账号，本库默认用 accounts[0]，可用 --account qq=账号名 指定。
- 只支持单聊（/v2/users/<openid>/messages），群聊是 /v2/groups/<group_openid>/messages。
- 主动推送（非回复）需要开放平台后台开通「主动消息」权限，否则报 403 或 40034。

## 四、微信（iLink Bot）

### 协议

```
POST https://ilinkai.weixin.qq.com/ilink/bot/sendmessage
Content-Type: application/json
AuthorizationType: ilink_bot_token
Authorization: Bearer <token>
iLink-App-Id: bot
iLink-App-ClientVersion: 131584
X-WECHAT-UIN: <随机 4 字节 base64url>

{
  "msg": {
    "from_user_id": "",
    "to_user_id": "***已脱敏***-邮箱",
    "client_id": "<uuid>",
    "message_type": 2,
    "message_state": 2,
    "item_list": [ { "type": 1, "text_item": { "text": "正文" } } ],
    "context_token": "<可选>"
  },
  "base_info": { "channel_version": "2.2.0" }
}
```

### 常量（与 dsh-bridge 的 lib/wechat/gateway.js:27-48 逐行核对一致）

| 常量 | 值 |
|---|---|
| ILINK_APP_ID | bot |
| CHANNEL_VERSION | 2.2.0 |
| ILINK_APP_CLIENT_VERSION | (2<<16) 位或 (2<<8) 位或 0 = **131584** |
| EP_SEND_MESSAGE | ilink/bot/sendmessage |
| EP_GET_CONFIG | ilink/bot/getconfig |
| EP_SEND_TYPING | ilink/bot/sendtyping |
| MSG_TYPE_BOT | 2 |
| MSG_STATE_FINISH | 2 |
| ITEM_TEXT | 1 |
| 单条上限 | 2000 字符 |

**注意没有 HMAC 签名。** 只需要 Bearer token 加那几个固定头。

### 当前状态：sendmessage 不通

2026-11-15 对 **9 个微信账号逐个实测**：

```
{ "ret": -2, "errmsg": "prepare failed" }
（HTTP 状态码 200，所以从 HTTP 层看不出来）
```

带 context_token 与不带，结果完全一样。

但**同一个 token 的其它 RPC 都正常**：

| RPC | 结果 |
|---|---|
| ilink/bot/getconfig | ret=0，返回 typing_ticket（600s TTL） |
| ilink/bot/sendtyping | ret=0 |
| ilink/bot/sendmessage | **ret=-2 prepare failed** |

**结论：token 有效、peer 有效，是 sendmessage 这条 RPC 对该 bot 本身不通。**

dsh-bridge 的 gateway.js:57-61 把 -2 + prepare failed 判为 isStaleSessionRet（会话/凭证过期），在这个场景下是**误判**。

### 修法

只能是**重新扫码绑定机器人**（人在微信客户端操作）。改参数、换 peer、换 token 都试过，无效。

### context_token 说明

存在 dsh-bridge 目录下的 wechat-context-tokens.json，结构是 peer 前缀 → 136 字符 token 的字典。协议规定过期返 ret=-14，此时本库会去掉 context_token 重试一次（照抄 gateway.js:455-513 的降级路径）。

### iLink 的独占锁约束（做轮询时必读）

1. **每条 bot token 只允许一个 poller**（getupdates 长轮询），第二个会收到 HTTP 403。
2. 会话过期（ret=-14 或 ret=-2 加 unknown error）要暂停轮询，不能无限重试。

本库**只做一次性 sendmessage、不轮询 getupdates**，所以不抢独占锁，可与 dsh-bridge 的机器人共存。

## 五、通道选择建议

| 场景 | 推荐 |
|---|---|
| 要最可靠 | telegram + feishu + qq 三条一起（默认） |
| 手机装了 Telegram | 只 telegram 就够 |
| 只想要国内 App 推送 | feishu（飞书 App 推送很稳） |
| 只装 QQ | --channels qq |
| 一定要微信 | 目前做不到，除非重新扫码修好机器人 |
