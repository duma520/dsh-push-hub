# 十二通道协议说明

本文件是 [README](../README.md) 的技术附录：把每个通道的**真实请求形态**、**凭据字段**、**成功判定**、**已知坑**写全，便于改代码或换账号时对照。

> **v0.2.0 起**：群晖 Chat 的 webhook 不再需要手工编辑配置文件 —— DSH 设置 → 「推送中枢」→「群晖 Chat」卡片里直接填即可，写进 `~/.dsh/dsh-push-hub/config.json`（权限 0600）。本文件仍保留手工写法，用于脚本批量配置或界面不可用时兜底。

所有通道的共同约定：

- 统一签名 `send(text, acc, options) → Promise<{ ok: boolean, detail: string }>`
- 内部按 `MAX_CHARS` 分块，块之间 `sleep(delayMs)`
- 任何网络异常都收敛成 `{ status: null, body: '异常描述' }`，**永不抛**
- `acc` 就是 `~/.dsh/dsh-push-hub/config.json` 里 `own_bots.<通道>[i]` 那一项（v0.10.0 起不再读 dsh-bridge）

> **v0.13.0 起通道从 5 个补到 12 个**：新增钉钉 / 企业微信（群机器人 + 自建应用）/ Slack / Discord / Matrix / 邮件。它们的完整说明从**第八节**起（钉钉 / 企业微信群机器人 / 企业微信自建应用 / Slack / Discord / Matrix / 邮件），第一节的字段总表也已补齐。

## 一、字段对照总表（最容易出错的地方）

插件从 Python 版移植时，把一批字段名译错了，导致「账号缺少 token」。真实字段以 dsh-bridge 落盘的为准：

| 通道 | 真实字段 | ❌ 写错就报「缺少」的写法 |
|---|---|---|
| telegram | `botToken`（46 字符）、`proxy`、`allowFrom` | `token`（插件里做成了兜底别名，不是主字段） |
| feishu | `appId`、`appSecret`、`domain`、`allowFrom` | `app_id` / `app_secret` |
| qq | `appId`、`appSecret`、`accountId`、`allowFrom` | `clientSecret` |
| wechat | `token`、`accountId`、`baseUrl`、`allowFrom` | — |
| synology_chat | `webhookUrl`（token 已嵌在 URL 里） | `resource`（HA 的叫法，插件里做成了兜底别名） |
| dingtalk | `webhookUrl`（整条 URL，token 在 `access_token=` 参数里）、`secret`（加签，选填，`SEC` 开头） | `accessToken`（插件里会从 URL 里抽，填裸 token 也行） |
| wecom | `webhookUrl`（整条 URL，key 是 UUID） | `key`（插件从 URL 里抽） |
| wecom_app | `corpId`、`corpSecret`、`agentId`、`proxy` | `corpid` / `secret` / `agentid`（大小写不对就读不到） |
| slack | `botToken`（`xoxb-` 开头） | `token`（当成 Telegram 那种写法会 401） |
| discord | `botToken` | `token` |
| matrix | `homeserver`（带协议）、`accessToken` | `server` / `token` |
| email | `smtpHost`、`smtpPort`、`user`、`pass`、`from`、`subject` | `host` / `port` / `password` |

**实现上全部写成了 `acc?.appId ?? acc?.app_id` 这种多级兜底**，所以两种写法都能跑；但配新账号时请按左列写。

## 二、Telegram

### 请求

```http
POST https://api.telegram.org/bot<botToken>/sendMessage
Content-Type: application/json

{"chat_id":"<allowFrom[0]>","text":"<块>","disable_web_page_preview":true}
```

### 必须走代理

本机直连 `api.telegram.org` 稳超时（`connect ETIMEDOUT`）。代理取自账号的 `proxy` 字段：

```json
{ "name": "135", "botToken": "<46 字符>", "proxy": "http://192.168.x.x:20808", "allowFrom": ["6317****92"] }
```

不配 `proxy` 时走全局 `fetch` 直连，结果就是超时。

### 成功判定

`status === 200 && data.ok === true`。少判 `ok` 会把「token 错」当成成功（TG 会用 200 配 `ok:false` 返回业务错）。

### 关键常量

- `MAX_CHARS = 4096`
- 块间隔 350ms

### 常见错

| 报错原文 | 原因 |
|---|---|
| `connect ETIMEDOUT 107.181.166.244:443` | `http.js` 的 `agent:false` 丢弃了代理隧道（v0.1.1 已修） |
| `不支持的 URL` / 404 `ok:false` | token 错或已被吊销 |
| `chat not found` | `allowFrom` 里的 chat_id 没和这个 bot 说过话 |

## 三、飞书 / Lark

### 第一步：换 tenant_access_token

```http
POST {host}/open-apis/auth/v3/tenant_access_token/internal
Content-Type: application/json

{"app_id":"<appId>","app_secret":"<appSecret>"}
```

`host` 由 `acc.domain` 决定：

| domain | host |
|---|---|
| `larksuite`（或含 `lark`） | `https://open.larksuite.com` |
| 其它/未填 | `https://open.feishu.cn` |

响应取 `tenant_access_token`。

### 第二步：发消息

```http
POST {host}/open-apis/im/v1/messages?receive_id_type=<chat_id|open_id>
Authorization: Bearer <tenant_access_token>
Content-Type: application/json

{"receive_id":"<对端>","msg_type":"text","content":"{\"text\":\"<块>\"}"}
```

### 两个必踩点

1. **`content` 必须是二次 JSON 字符串**。飞书的 `content` 类型是 `string`，里面再装一层 JSON。给对象直接参数错：

   ```js
   content: JSON.stringify({ text: 块 })   // ✅
   content: { text: 块 }                    // ❌
   ```

2. **`receive_id_type` 按前缀选**：

   | 对端 ID 前缀 | receive_id_type | 含义 |
   |---|---|---|
   | `oc_` | `chat_id` | 群 |
   | 其它 | `open_id` | 个人 |

   写错会报 `invalid receive_id`。

### 成功判定

`status === 200 && (code === 0 || code === null)`。飞书成功时 `code: 0`。

### 关键常量

- `MAX_CHARS = 2000`
- 块间隔 350ms

## 四、QQ（QQ 开放平台机器人）

### 第一步：换 app access token

```http
POST https://bots.qq.com/app/getAppAccessToken
Content-Type: application/json

{"appId":"<appId>","clientSecret":"<appSecret>"}
```

响应取 `access_token`。

### 第二步：发消息

```http
POST https://api.sgroup.qq.com/v2/users/<openid>/messages
Authorization: QQBot <access_token>
Content-Type: application/json

{"content":"<块>","msg_type":0}
```

### 最大的坑：授权头前缀

```
Authorization: QQBot <access_token>     ✅
Authorization: Bearer <access_token>    ❌ 一律 401
```

这是 QQ 开放平台独有的 —— 它不用 OAuth 的 `Bearer` 方案。

### 成功判定

`status === 200 || status === 201`。**别只判 200**：新会话发第一条时平台常回 201。

### 关键常量

- `MAX_CHARS = 1800`
- 块间隔 350ms

## 五、微信（iLink 机器人）

### 请求

```http
POST {baseUrl}/ilink/bot/sendmessage
AuthorizationType: ilink_bot_token
iLink-App-Id: bot
iLink-App-ClientVersion: 131584
X-WECHAT-UIN: <每次随机 base64url(4 字节)>
Authorization: Bearer <token>
Content-Type: application/json

{
  "msg": {
    "from_user_id": "",
    "to_user_id": "<allowFrom[0]>",
    "client_id": "pushhub-<时间戳>-<随机数>",
    "message_type": 2,
    "message_state": 2,
    "item_list": [{ "type": 1, "text_item": { "text": "<块>" } }],
    "context_token": "<可选>"
  },
  "base_info": { "channel_version": "2.2.0" }
}
```

`baseUrl` 默认 `https://ilinkai.weixin.qq.com`。

### 常量含义

| 常量 | 值 | 含义 |
|---|---|---|
| `ILINK_APP_ID` | `bot` | 固定 |
| `CHANNEL_VERSION` | `2.2.0` | base_info.channel_version |
| `ILINK_APP_CLIENT_VERSION` | `131584` | `(2<<16)\ | (2<<8)\ | 0` |
| `MSG_TYPE_BOT` | 2 | message_type |
| `MSG_STATE_FINISH` | 2 | message_state |
| `ITEM_TEXT` | 1 | item_list[].type |
| `RET_CONTEXT_INVALID` | -14 | context_token 失效 |

### context_token 处理

从 `~/.dsh/dsh-bridge/wechat-context-tokens.json` 按 peer 读：

```js
data?.[peer] ?? data?.tokens?.[peer]
// 若是对象，再取 .context_token / .contextToken
```

读到就带上；服务端回 `ret === -14` 时**去掉它重试一次**（这是常见的可恢复错误）。

### 已知故障（重要）

2026-11-15 实测，9 个账号全部命中：

```
HTTP 200  {"ret": -2, "errmsg": "prepare failed"}
```

同一 token 打 `getconfig` / `sendtyping` 却是 `ret = 0`。

**结论**：不是参数错，是这个 bot 的 sendmessage RPC 本身没就绪。改头、改 body、改 baseUrl 全都无效。
**唯一修法**：人在微信客户端重新扫码绑定该 bot。

因此微信在 `bus.BEST_EFFORT` 集合里 —— 它失败不影响整体 `ok`。

### 成功判定

`status === 200 && (ret === 0 || ret === null)`。

### 关键常量

- `MAX_CHARS = 2000`，实际 `limit = max(200, configured - 20)`（留 20 字余量，避免贴上限被服务端判超长）
- 块间隔 350ms

## 六、群晖 Chat（本项目新增）

### 协议取证

来源：Home Assistant core 的 `homeassistant/components/synology_chat/notify.py`。

它做的是一次 `POST`：

```python
resource = config[CONF_RESOURCE]          # 用户自建 incoming webhook URL
payload  = {"text": message}              # 可选 file_url
requests.post(resource, data={"payload": json.dumps(payload)})
```

要点：

1. body 是 **`application/x-www-form-urlencoded`**，只有一个字段 `payload`，其值是 JSON 字符串。
2. token 已经嵌在 webhook URL 里（`...&token=%22xxxx%22`），所以配置**只要 webhookUrl**。
3. 成功**只认 HTTP 200 / 201**（这点和别的通道不同）。

### 请求

```http
POST <webhookUrl>
Content-Type: application/x-www-form-urlencoded

payload={"text":"<块>"}
```

对应实现就是 `postForm(url, { payload: JSON.stringify({ text: 块 }) })` ——
`postForm` 内部用 `URLSearchParams` 做编码，会自动把 `{"text":"..."}` 转义成合法表单值。

### 配置

```json
{
  "synology_chat": {
    "accounts": [
      {
        "name": "群晖 Chat",
        "type": "incoming",
        "webhookUrl": "https://你的NAS:5001/webapi/entry.cgi?api=SYNO.Chat.External&method=incoming&version=2&token=%22你的TOKEN%22",
        "sendChunkDelayMs": 1500,
        "maxMessageChars": 2000
      }
    ]
  }
}
```

在群晖 Chat 里生成 webhook 的路径：**整合（Integrations）→ 传入 Webhook（Incoming Webhook）→ 新增**，复制它给的 URL。

### 成功判定

`status === 200 || status === 201`。302 算失败（说明被重定向到登录页，通常 URL 里的 token 不对）。

### 三种整合类型（type 字段，v0.40.0 起对齐群晖面板）

群晖 Chat 的「整合」里能建三种东西，**数据流向不同、能力不同**。账号的 `type` 字段与之一一对应：

| | `type: "incoming"`（默认） | `type: "outgoing"` | `type: "bot"` |
|---|---|---|---|
| 面板上的名字 | 整合 → **传入的 Webhook** | 整合 → **发出的 Webhook** | 整合 → **机器人** |
| 方向 | 插件 → 群晖 ✅ | 群晖 → 你填的 URL ❌ | 传入 URL：插件 → 群晖 ✅；传出 URL：群晖 → 你 ❌ |
| 端点 | 用户自建的整条 URL | 你自己服务器上的回调地址 | `{NAS}/webapi/entry.cgi?api=SYNO.Chat.External&method=chatbot&version=2&token=…` |
| 必填 | `webhookUrl`（或 `nasUrl` + `token`，见下） | `outgoingUrl` + `token`（`channel` / `triggerWord` 选填） | `incomingUrl`（或 `nasUrl` + `token`）+ `userIds` |
| 能发到 | 该 webhook **绑定的那个频道** | **不能发**，本插件只登记 | 只能**点对点**（`user_ids` 是数字用户 ID） |
| 只读探测 | ❌ 无接口（调任何只读方法都返回 404） | ❌ 直接说明不参与发送 | ✅ `channel_list` / `user_list` |

**关于 `outgoing`（发出的 Webhook）为什么发不出消息**：面板上那个 URL 栏的提示是「Synology Chat 会在事件发生时向该 URL 发送请求」，令牌的作用是**你这一侧验签**群晖发来的请求 —— 它不是「往群晖发消息」的凭据。协议上不存在用它对群晖发消息的接口。同理，它也是接收方向，DSH 宿主只监听 `127.0.0.1:9429`，NAS 连不进来，所以本插件既不发送也不接收，只把 URL / 令牌 / 频道 / 触发字登记下来备查（`send()` 遇到 `outgoing` 不发任何网络请求，直接返回中文原因）。

**兼容**：老配置里 `type` 是 `"webhook"` 或干脆没写（`undefined`），一律按 `incoming` 处理 —— 它们原本走的就是 incoming 那套协议，语义完全一致，行为不变。归一函数是 `channels/synology.js` 的 `normalizeType()`。

**webhookUrl 可以省略**：只拿到 64 位令牌是很常见的情况，所以 `resolveWebhookUrl()` 支持「`nasUrl` + `token` 自动拼成 incoming URL」（`?api=SYNO.Chat.External&method=incoming&version=2&token=…`）。填了完整 URL 则原样使用，不重复拼 `entry.cgi`。机器人同理走 `resolveBotUrl()`（优先 `incomingUrl`，否则 `nasUrl` + `token` 拼 chatbot 端点）。

### `nasUrl` 与 `incomingUrl` 到底该填什么（v0.10.0 补，踩过两次）

群晖机器人面板上给的是三项：**传入 URL**、**传出 URL**、**令牌**。

- `incomingUrl`（机器人类型专用）= 面板的**传入 URL**，直接填整条就能发；留空则用 `nasUrl` + `token` 自动拼。
- `nasUrl` = NAS 的基地址（例 `https://xxx.quickconnect.cn:5001`），配合 `token` 让后端拼端点。
- `token` = 面板的**令牌**（64 位）。
- `outgoingUrl` / `outgoing` 类型的那个 URL = 面板的**传出 URL**，**只是登记** —— 那是群晖回调你的地址（接收方向），DSH 宿主只监听 `127.0.0.1`，填了也不会生效。

实测四种填法（token 相同）：

| 填进 `nasUrl` | 结果 |
|---|---|
| `https://192-168-1-10.xxxx.quickconnect.cn:65001/webapi/entry.cgi` | ✅ `token 可用；可见 0 个频道、38 个用户` |
| 同上不带 `/webapi/entry.cgi` | ✅ 同上（`nasEntry()` 自动补） |
| 同上不写协议 / 带尾斜杠 | ✅ 同上（自动补 `https://`、去尾斜杠） |
| `http://192.0.2.65:65001` | ❌ `HTTP 400：400 The plain HTTP request was sent to HTTPS port` |
| `https://192.0.2.65:65001` | ❌ `连不上 NAS: TypeError: fetch failed`（NAS 自签证书 `ERR_TLS_CERT_ALTNAME_INVALID`） |

**结论：用 QuickConnect 的传入 URL 域名，别用局域网 IP。** QuickConnect 域名有有效证书，Node 的 `fetch` 认；局域网 IP 是自签证书，`lib/http.js` 的 `direct()` 走全局 `fetch`，**无法关掉证书校验**（也刻意不加 `insecure` 开关）。

v0.10.0 起这类网络错误会被 `explainNet()` 翻成可操作文案：看到 `plain HTTP request was sent to HTTPS port` 就是协议写错了（5001/65001 都是 HTTPS），看到 `fetch failed` / `ALTNAME_INVALID` 就是撞了自签证书、要换 QuickConnect 域名。
### 错误码翻译（`explainChatError`）

DSM 7.3.2 / Chat Server 2.4.5 实测下来的 `error.code`，最容易误判的是 **404**：

| code | 含义 | 实际原因 |
|---|---|---|
| 101 | 参数不对 | token 或 `user_ids` 格式错 |
| 102 | API 不存在 | 没装 / 没启用 Chat Server |
| 103 | 方法不存在 | Chat Server 版本过旧 |
| **404** | **token 类型不对** | **webhook token 调只读接口（`channel_list` / `user_list`）恒返回它** —— 不是地址写错 |
| 401 | bot 不是频道成员 | 先在群晖 Chat 里把它拉进频道 |
| 119 | 权限不足 | 当前身份没有该权限 |

### 三件做不到的事（协议限制，不是没实现）

1. **没有「发私聊」API**：DM 是「成员恰好 2 人的匿名/私有频道」，要用 DSM 会话（用户名密码）走 `SYNO.Chat.Post.create` 才能发；bot token 只能 `chatbot` + `user_ids`。
2. **API 创建的 webhook token 不能发消息**：只有群里 UI 手动创建的才被 `SYNO.Chat.External` 接受。
3. **接收方向（发出的 Webhook / 斜杠命令 / 应用程序整合）需要公网回调 URL**：DSH 宿主只监听 `127.0.0.1`，外部平台无法回连，所以这三项不在本插件职责内。

### 关键常量

- `MAX_CHARS = 2000`
- 块间隔 **1500ms**（比别的通道慢 4 倍，因为自建 webhook 吞吐低，连发容易被限）

## 七、新增一个通道要改哪几处（v0.13.0 重写）

老版本这一节只列了 5 步，实际漏了三处 —— 照着改会出现「能发，但界面里看不到这个通道」。v0.13.0 补 7 个通道时踩实了，完整清单是 **8 处**：

| 位置 | 改什么 | 漏了会怎样 |
|---|---|---|
| `lib/channels/<name>.js` | 新建文件，导出 `NAME` / `MAX_CHARS` / `TITLE` / `send` / `probe` | 没通道实现 |
| `lib/bus.js` | `import` + `REGISTRY` 加一行 | `registryCoversAll = false`，发不出去 |
| `lib/bus.js` | 需要的话加进 `BEST_EFFORT` | 软通道失败会拖垮整批 |
| `lib/config.js` | `ALL_CHANNELS` 加名字 + `DEFAULT_PROXY.channels` 加一个 `false` | 代理开关对它不生效（`proxyPolicy` 只遍历 `ALL_CHANNELS`） |
| `lib/index.js` | `TARGET_META` 加一段 | 「发送到」下拉没有这个通道的类型与提示 |
| `lib/index.js` | `OWN_BOT_FIELDS` 加一段 | 界面里出不了账号卡 |
| `lib/client.js` | `CHANNEL_TITLES` / `CHANNEL_ORDER` / `LOGO_CLASS` / `LOGO_TEXT` / `OWN_HINTS` / `TARGET_PLACEHOLDERS` / `PROXY_HINTS` 七张表 | 左栏不显示、logo 是问号、没有提示文案 |
| 两份 CSS | `.dph-logo<Name>` 一行（`lib/theme.js` **与** `lib/client.js` 内联 `THEME_CSS`） | logo 没颜色（透明底 + 白字，看不见） |

改完必做：

```powershell
cd <插件根目录>\dsh-push-hub
node --check lib\channels\<name>.js
node scaffold\probe_apply.mjs    # registryCoversAll = true，listChannels 里能看到新名字
node scaffold\probe_proxy.mjs    # B4 按 ALL_CHANNELS.length 动态断言，跟着通道数走
node scaffold\probe_proxy_ui.mjs # 代理页要能渲染出新通道那一行
node scaffold\probe_newui.mjs    # 左栏要有新通道
```

然后「禁用 → 启用」插件（宿主 ESM 缓存不刷新），再 `GET /@duma520/dsh-push-hub/api/info` 确认 `version` 变了。

## 八、钉钉（群自定义机器人，v0.13.0 新增）

### 请求

```
POST https://oapi.dingtalk.com/robot/send?access_token=<token>[&timestamp=<ms>&sign=<urlencoded base64>]
Content-Type: application/json

{"msgtype":"text","text":{"content":"消息正文"}}
```

### 加签（机器人安全设置里勾了「加签」才需要）

```js
const timestamp = Date.now()
const stringToSign = timestamp + '\n' + secret
const sign = createHmac('sha256', secret).update(stringToSign).digest('base64')
// 两个都作为查询参数追加，sign 必须 encodeURIComponent
```

`secret` 必须以 `SEC` 开头。**少这一步会一直报 `310000`（加签校验失败）**。

### 成功判定

HTTP 200 **且** `errcode === 0`。

| code | 含义 |
|---|---|
| 300001 | token 无效 |
| 300005 | 关键词不匹配（机器人安全设置里勾了「自定义关键词」，正文里必须包含） |
| 310000 | 加签校验失败（`secret` 错或没带 `timestamp`/`sign`） |
| 130101 | 触发频率限制（每分钟 20 条） |

### 为什么只做群机器人、不做内部应用

| 项 | 值 |
|---|---|
| `NAME` | `dingtalk` |
| `MAX_CHARS` | 3000 |
| `TITLE` | `钉钉` |
| 软通道 | ✅ 是（没有只读探测接口） |

## 九、企业微信（群机器人，v0.13.0 新增）

### 请求

```
POST https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<UUID>
Content-Type: application/json

{"msgtype":"text","text":{"content":"消息正文","mentioned_list":["zhangsan","@all"]}}
```

`mentioned_list` 只在**最后一块**带 —— 每块都带会让人被重复提醒。

### 为什么 `MAX_CHARS` 只有 600

群机器人单条上限是 **2048 字节**，不是字符。中文按 UTF-8 占 3 字节 → 600 × 3 = 1800，留富余。给 2000 会被服务端截断或直接报错。

### 成功判定

HTTP 200 **且** `errcode === 0`。

| code | 含义 |
|---|---|
| 93000 | Webhook 地址无效 |
| 45009 | 接口调用超过限制（每分钟 20 条） |
| 40058 | 参数不合法 |
| 40008 | 消息类型不合法 |
| 40014 | key 无效（把 corpsecret 当 key 填了） |

`key` 是 UUID 形状（`/^[0-9a-fA-F-]{32,40}$/`），`probe()` 靠这个做形状校验。

## 十、企业微信（自建应用，v0.13.0 新增）

### 两步

```
① GET https://qyapi.weixin.qq.com/cgi-bin/gettoken?corpid=<企业ID>&corpsecret=<应用Secret>
   → {"errcode":0,"access_token":"...","expires_in":7200}

② POST https://qyapi.weixin.qq.com/cgi-bin/message/send?access_token=<token>
   {"touser":"zhangsan|@all","msgtype":"text","agentid":1000002,"text":{"content":"正文"}}
```

### 为什么每次发送都重新换 token、不缓存

企业微信的 `access_token` 是**全局单例**（同一个应用只能有一个有效 token）。别的程序换过一次就把你这颗顶掉，缓存反而更容易出「token 失效」。多一次网络请求换稳定，值。

### 成功判定

`errcode === 0`。此时**还要看 `invaliduser`**：部分成员无效也算成功，但要在 `detail` 里点出来「这些账号没发出去」。

| code | 含义 |
|---|---|
| 40001 | Secret 错 |
| 40013 | corpId 错 |
| 40056 | agentId 错 |
| 40014 | token 失效 |
| **60020** | **IP 不在可信列表 —— 最常踩**：企业微信应用必须把本机公网 IP 加进「企业可信IP」 |
| 81013 | 成员不存在 |
| 45009 | 超频 |

## 十一、Slack（v0.13.0 新增）

### 请求


| `not_in_channel` | 机器人在工作区但不在这个频道 |
| `is_archived` | 频道已归档 |

| `msg_too_long` | 超过 4000 字符 |

## 十二、Discord（v0.13.0 新增）

### 请求

```
POST https://discord.com/api/v10/channels/<channelId>/messages
Authorization: Bot <token>
Content-Type: application/json

{"content":"消息正文"}
```

### 两个坑

1. **成功是 200，不是 201**。REST 惯例里创建资源通常回 201，Discord 这里回 200。写成 `status === 201` 会永远判失败。
2. **授权头是 `Bot <token>`**，不是 `Bearer <token>`——写成 Bearer 会 401。

### 「发送到」要填什么

**频道 ID（纯数字 Snowflake）**，不是频道名。取法：Discord 设置 → 高级 → 打开「开发者模式」，然后右键频道 → 复制频道 ID。

### 429 限流

响应体带 `retry_after`（秒）。本插件把它写进 `detail` 但**不自动重试** —— 重试会越限越深。

### 错误码翻译

| code | 含义 |
|---|---|
| 50001 | 缺权限（`View Channel` / `Send Messages`） |
| 50007 | 发不到该用户（对方关了私信） |
| 10003 | 频道不存在 |
| 10004 | 服务器不存在 |
| 40001 | token 无效 |
| 50035 | 内容格式不对（空消息 / 超 2000 字符） |

## 十三、Matrix（v0.13.0 新增）

### 请求

```
PUT https://<homeserver>/_matrix/client/v3/rooms/<roomId>/send/m.room.message/<txnId>
Authorization: Bearer <accessToken>
Content-Type: application/json

{"msgtype":"m.text","body":"消息正文"}
```

### 为什么用 PUT + txnId

Matrix 的发送语义是**幂等**的：`txnId` 是去重键，同一个 `txnId` 重发不会在房间里落两条。本插件的 `txnId` 是 `'dsh' + Date.now() + '-' + <块序号>`，同一设备内唯一。

### 成功判定

HTTP 200 且响应体带 `event_id`。

### 错误码翻译

| errcode | 含义 |
|---|---|
| `M_UNKNOWN_TOKEN` | token 无效 |
| `M_MISSING_TOKEN` | 没带 Authorization 头 |
| `M_FORBIDDEN` | 不在这个房间 |
| `M_NOT_FOUND` | 房间不存在 |
| `M_LIMIT_EXCEEDED` | 触发限流 |
| `M_UNKNOWN` / `M_UNRECOGNIZED` | 服务端不认识这个请求 |

### 刻意不支持加密房间

加密房间要用房间的**会话密钥**对每条消息做加密，还要处理密钥分发与设备验证。本插件不做这件事——遇到加密房间会**如实报错**，而不是把明文发出去假装成功。

### 凭据怎么取

Element → 设置 → 帮助与关于 → 访问令牌。`homeserver` 例 `https://matrix.org`（要带协议，不要带尾斜杠）。

## 十五、多投递目标（v0.14.0 新增）

一个机器人可以同时发到多个会话。配置里是 `own_bots.<通道>[i].targets` 数组，每项 `{ kind, id }`。

### 解析顺序（`lib/mentions.js` 的 `targetsOf()`）

| 顺序 | 读什么 | 说明 |
|---|---|---|
| 1 | `acc.targets` 数组 | 过滤非对象项、`id` 为空、`id` 重复；`kind` 不合法归一成 `auto` |
| 2 | `acc.target` 单个对象 | v0.6.0 以来的老字段，数组为空时回落 |
| 3 | `acc.allowFrom[0]` | 最老的 ` 白名单首项，前两者都没有才用 |

三条都没有 → 返回空数组，交给通道自己报「还没填发送到」（文案由通道给，因为各通道要填的 ID 形态不同：`chat_id` / `ou_` / `openid` / `o9cq…` / 数字 user_id）。

### 扇出在哪一层

在 `lib/bus.js` 的 `sendToTargets()`，不在通道里。理由：12 个通道的 `send()` 都只认 `acc.target` 一个值，把扇出下沉意味着改 12 个文件、各写一遍分块与失败统计，改一次要验 12 次。

| 目标数 | 行为 |
|---|---|
| 0 | 原样调 `mod.send`，让通道报它自己的「还没填发送到」 |
| 1 | `mod.send(body, { ...acc, target: targets[0] })` —— 仍然显式钉住，防 `allowFrom` 回落发错人 |
| ≥2 | 逐个调，收集 `deliveries`；全成功才 `ok: true`；否则 detail 点名哪个 ID 失败 |

### 兼容性

- **只写 `target` 不写 `targets`**：与 v0.13.0 行为完全一致。
- **只写 `targets` 不写 `target`**：发送正常（第 1 步就命中）；但界面上保存一次会把首条同步写回 `target`。
- **两个都写且不一致**：以 `targets` 为准，`target` 被首条覆盖。

### 各通道的注意事项

| 通道 | 多目标是否合适 | 说明 |
|---|---|---|
| Telegram | ✅ | 单聊 + 群都行；受 Bot API 速率限制（约 30 条/秒） |
| 飞书 | ✅ | 多群 + 多人都行；` 提醒按 `mention` 全局一份，不按目标区分 |
| QQ | ✅ | 需要各自的 `openid` / `group_openid`，且机器人得先在群里被 ` 过 |
| 微信 | ⚠️ | iLink 是点对点，多个 `o9cq…` 就是发给多个人 |
| 群晖 Chat | ⚠️ | webhook 天然只发到生成它的那个频道，配多个 targets 无意义；bot 只能点对点 |
| 钉钉 / 企微群机器人 | ⚠️ | 群机器人 Webhook 绑定固定群，多目标无意义（各自的 webhook 要用不同账号） |
| 企微自建应用 | ✅ | `touser` 支持竖线分隔的多个成员 |
| Slack / Discord / Matrix | ✅ | 多个频道/房间都行；注意 429 限流 |
| 邮件 | ✅ | 多个收件人；但每次是独立一封邮件（不是抄送） |

### 新增通道时要注意的一条（v0.14.0 起）

除第七节那 8 处之外，新通道的 `send()` **必须仍然只认 `acc.target` 一个值** —— 多目标扇出统一在 `lib/bus.js` 的 `sendToTargets()` 里做，通道自己不要读 `acc.targets`。若某通道天然只发一个地方（如钉钉/企微群机器人 Webhook），在 `TARGET_META` 里把 `kinds` 留空数组即可，界面就不会渲染「发送到」，用户也就不会误以为能配多个。

## 十六、账号级高级字段（v0.17.0 新增）

十二个通道的实现都在读下面这四个字段，但界面到 v0.16.0 为止只给 telegram / wecom_app 开了「代理」一个入口。v0.17.0 在机器人卡加了第四页「高级」，把四个都摆出来。

### 16.1 四个字段

| 字段 | 界面文案 | 类型 | 读取位置 | 留空的行为 |
|---|---|---|---|---|
| `proxy` | 代理 | 文本 | `lib/bus.js:73`（`withChannelProxy`）+ 各 `channels/*.js` 的 `acc.proxy` | 回落到通道级「代理通道」开关 |
| `maxMessageChars` | 分块长度 | 数字 | 各 `channels/*.js` 的 `Number(acc?.maxMessageChars) > 0 ? … : MAX_CHARS` | 用该通道写死的 `MAX_CHARS` |
| `chunkDelayMs` | 块间延迟（毫秒） | 数字 | `lib/bus.js` 的 `sendToTargets()` 折成 `options.delayMs` | 用该通道写死的默认延迟 |
| `allowSelfSigned` | 允许自签证书 | 布尔（仅邮件） | `lib/channels/email.js:91` / `:141` | 正常校验 TLS 证书 |

### 16.2 各通道的默认上限与默认延迟（留空时就是这些值）

| 通道 | `MAX_CHARS` | 默认 `delayMs` | 备注 |
|---|---|---|---|
| telegram | 4096 | 350 | 平台硬上限 4096，填更大没意义 |
| feishu | 2000 | 350 | |
| qq | 1800 | 350 | |
| wechat | 2000 | 350 | |
| matrix | 30000 | 500 | 房间消息上限很高，但一次 sync 拉太多会慢 |
| discord | 1900 | 600 | 平台硬上限 2000，留 100 余量 |
| slack | 3800 | 1100 | `chat.postMessage` 有严格限流，1100 是实测安全值 |
| dingtalk | 3000 | 1200 | 加签请求也走同一限流 |
| wecom | 600 | 1200 | 群机器人单条上限 4096 字节，中文按 3 字节算所以取 600 字 |
| wecom_app | 600 | 1200 | 同上 |
| synology_chat | 2000 | 1500 | |
| email | 100000 | — | 不分块，一封一封发 |

### 16.3 后端处理三种类型（`lib/index.js`）

- **掩码**：按 `field.type` 分派。数字空值给 `''`、有值给 `Number`；布尔给真布尔。**不能一律 `String(...)`** —— 那会把「清空」变成 `Number('')` 即 `0`，回写后分块逻辑直接失效。
- **合并**：数字遇到空值 `continue`（不沿用旧值，否则改回默认永远改不掉）；要求 `Number.isFinite(n) && n > 0` 才写；布尔未传时只在旧值 `true` 时保留。
- **算不算「有账号」**：`hasCredential` 过滤 `group === 'advanced'`，避免「只勾了个复选框」的空壳账号留在列表里。

### 16.4 账号级延迟怎么盖过全局（`lib/bus.js`）

```js
const ownDelay = Number(acc?.chunkDelayMs)
const effective = Number.isFinite(ownDelay) && ownDelay >= 0 ? { ...options, delayMs: ownDelay } : options
```

三条发送分支（0 目标 / 单目标 / 多目标扇出）**全部**用 `effective`。判据是 `>= 0` 不是 `> 0`：延迟 0 是合法配置（不分块时立刻发）。

### 16.5 加新通道时要跟着做的两件事

1. 通道实现里**继续读 `acc.proxy` / `acc.maxMessageChars`**（保持现状即可，`OWN_BOT_FIELDS` 的循环会自动给新通道补上这三个字段）。
2. 如果新通道有「只有它才有的账号级开关」（像邮件的 `allowSelfSigned`），在 `OWN_BOT_FIELDS.<通道>.push({..., type: 'boolean' | 'number', group: 'advanced'})` 里加，**不要**放进 `ADVANCED_FIELDS`（那是全通道共用的）。

## 十七、发文件（v0.18.0 新增）

十二个通道里能发附件的只有**五个**，而且它们上传的方式**四家各不相同** —— 这一节把四套协议和共用的那层写清。

### 17.1 谁支持、谁不支持

| 通道 | 能发文件 | 上传方式 |
|---|---|---|
| Telegram | 是 | 单请求 multipart（图片走 `sendPhoto`，其余 `sendDocument`） |
| Slack | 是 | 三段式：预签名地址 → 裸字节 → 绑定频道 |
| Discord | 是 | 单请求 multipart（必须带 `payload_json.attachments`） |
| Matrix | 是 | 两段式：先 `media/v3/upload` 拿 `mxc://`，再发 `m.room.message` |
| 邮件 | 是 | SMTP 附件（nodemailer） |
| 飞书 / 钉钉 / 企业微信（群机器人 + 自建应用）/ QQ / 微信 / 群晖 Chat | 否 | 这些平台都没有现成的附件上传路径 |

实测清单不在代码里硬编码，而是从「注册表里哪些模块有 `sendFile` 方法」动态算出来：

```js
export const FILE_CHANNELS = Object.freeze([...REGISTRY.entries()]
  .filter(([, mod]) => typeof mod.sendFile === 'function')
  .map(([name]) => name))
```

### 17.2 四套协议各自的坑

**Telegram**：图片走 `sendPhoto`（客户端会渲染预览），其余走 `sendDocument`。判据是 `isImageMime()`。`caption` 上限 1024 字符，超了截断。

**Discord**：`payload_json` 里必须写 `attachments: [{ id: 0, filename }]`，文件字段名是 `files[0]`。
**少了 `attachments` 这段描述，Discord 照回 200 但消息里没有文件** —— 这是最容易「测试通过、用户投诉」的一条。

**Slack**：老教程里的 `files.upload` 已停用。现在是：
1. `files.getUploadURLExternal` 拿一次性 `upload_url` + `file_id`
2. **裸字节** POST 那个地址（不是 multipart，**也不能带 Authorization** —— 地址本身是预签名的）
3. `files.completeUploadExternal` 带 `{ files: [{ id, title }], channel_id }` 绑进频道

第 2 步成功但第 3 步失败时，文件在 Slack 侧是「已上传未绑定」状态，会占着那份临时空间直到平台清理。错误文案如实写「文件已上传但绑定频道失败」，不谎称完全没发生。

**Matrix**：先 `POST /_matrix/media/v3/upload?filename=…` 拿 `content_uri`（必须校验以 `mxc://` 开头），再 PUT 一条 `m.room.message`，`msgtype` 是 `m.image` 或 `m.file`，`info` 里带 `mimetype` 与 `size`，`txnId` 用 `'dshfile' + Date.now()` 保证幂等。

### 17.3 为什么 multipart 是手写的

`lib/http.js` 有两条发送路径：直连走 `fetch`、走代理走「CONNECT 隧道 + `http.request` 自拼 headers」。

全局 `FormData` 在**第二条路上拿不到序列化好的字节** —— 结果是「直连能发、走代理发出去 0 字节文件」，而平台还回 200。这种分裂只有走代理的用户会踩到，最难查。

所以 `buildMultipart(fields, file)` 直接返回 `{ body: Buffer, contentType }`，两条路吃同一份字节：

```js
const built = buildMultipart(fields, { field: 'document', fileName, bytes, mediaType })
// built = { body: <Buffer>, contentType: 'multipart/form-data; boundary=----dsh…' }
```

它处理了四个细节：数组字段重复出现（`chat_id` 可能一次给多个）、`null` / `undefined` 跳过、中文文件名转义、文件部分自带 `Content-Type`。

### 17.4 读盘的三条纪律

**① 相对路径直接拒绝。** `readForSend()` 第一道判据是 `path.isAbsolute()`。
插件的 cwd 是 DSH 进程目录，不是用户心里的那个目录 —— 用户填 `报告.pdf` 时，如果恰好同名文件存在，就会**静默发出去一份无关文件**。这比报错危险：报错用户会改，静默发错的消息收不回来。

**② 文件只读一次盘。** `bus.sendFile()` 在循环外调一次 `readForSend`，同一份 `Buffer` 交给所有通道与所有目标。

由此派生一条**通道实现必须遵守的约定**：`sendFile` 里绝不能就地改 `bytes`（比如补文件头），否则多目标扇出时第二个目标收到的是坏文件。

**③ 平台上限逐通道把关。** `PLATFORM_LIMIT`：

| 通道 | 上限 |
|---|---|
| Telegram | 50 MB |
| Discord | 25 MB |
| Slack | 1 GB |
| Matrix | 50 MB |
| 邮件 | 25 MB |

注意 `maxMessageChars`（分块长度）**不影响附件** —— 附件体积只看这张表。给 Telegram 填 10000 的分块长度不会让 60 MB 的文件发得出去。

### 17.5 加新通道的文件支持要改哪几处

1. 通道里加 `export async function sendFile(file, acc, options)`，返回 `{ ok, detail? }`。
2. 收 `file` 的结构是 `{ fileName, bytes: Buffer, mediaType, size, path }`（由 `readForSend` 给出）—— **读它，不要改它**。
3. `lib/files.js` 的 `PLATFORM_LIMIT` 加这个平台的上限。
4. 如果平台的 `caption` 有长度上限，在 `sendFile` 里自己截（参照 Telegram 的 `caption.slice(0, 1024)`）。
5. 加完 `FILE_CHANNELS` 会自动带上它，**不用改 `lib/bus.js` 与前端**（前端从 `GET /send/file/channels` 拿清单）。

### 17.6 实测命令

```powershell

node scaffold\probe_file.mjs
# 期望：FILE_OK （88 项断言）
```

## 十八、WebSocket 接收：Slack Socket Mode 与 Discord Gateway（v0.19.0 新增）

### 18.1 为什么这一层要单独存在

到 v0.18.0，能收的四个通道里三个是长轮询（`getUpdates` / `getupdates` / `/sync`），一个是 SDK 封装的长连接（飞书 `WSClient`）。v0.19.0 补的这俩是**裸 WebSocket**：平台给一个 `wss://` 地址和一串 JSON 帧，握手、心跳、重连全得自己写 —— 所以新增 `lib/ws.js`。

它只做两件最小的事：把连接建起来、把帧读成字符串。协议语义全在 `lib/receiver.js` 的两个 worker 里。

### 18.2 本机实测：Node 内置 WebSocket 不接受代理

| 试法 | 结果 |
|---|---|
| `typeof globalThis.WebSocket` | `'function'`（Node v24.21.0 已内置） |
| `new WebSocket('wss://gateway.discord.gg/?v=10&encoding=json')` | **error 事件，`message` 为空** |
| `new undici.WebSocket(url, { dispatcher: new undici.ProxyAgent(p) })` | **收到 `{"op":10,"d":{"heartbeat_interval":41250}}`** |

Node 内置的 `WebSocket` 是全局对象，**不给 `dispatcher` 注入点**，这与 v0.13.0 踩过的 `fetch` 是同一个毛病（`lib/http.js` 为此手写了 CONNECT 隧道）。所以 `lib/ws.js` 从 DSH profile 借 `undici`：

```js
const req = createRequire(path.join(PROFILE_NODE_MODULES, 'noop.js'))
const undici = req('undici')
new undici.WebSocket(url, { dispatcher: new undici.ProxyAgent(proxy) })
```

借不到时 `loadUndici()` 返回 `null` 并把原因存进 `undiciError()`，**不抛 `ERR_MODULE_NOT_FOUND`** —— 与借飞书 SDK、借 nodemailer 是同一套约定。

### 18.3 Slack Socket Mode

**要什么**：App Token（`xapp-` 开头，Basic Information → App-Level Tokens，scopes 勾 `connections:write`）。**不是**发消息那把 Bot Token（`xoxb-`）。

**握手**

```text
POST https://slack.com/api/apps.connections.open
Headers: Authorization: Bearer xapp-...
  -> { ok: true, url: 'wss://wss-primary.slack.com/link/?ticket=...' }
```

URL 是一次性的，断开后必须重新换。`slackWorker.run()` 每次重连都会重新调一次这个接口。

**帧**

```text
<- { "type": "hello", "connection_info": { "app_id": "A123" } }
<- { "type": "events_api", "envelope_id": "e1", "payload": { "type": "event_callback", ... } }
-> { "envelope_id": "e1" }
<- { "type": "disconnect", "reason": "warning" }
```

**三个坑**

| 坑 | 后果 | 本项目的做法 |
|---|---|---|
| 用 Bot Token 调 `apps.connections.open` | 回 `not_allowed_token_type`，看不出是钥匙错了 | 填之前先判前缀，非 `xapp-` 直接回中文「看起来是 Bot Token」 |
| 不回 `envelope_id` | Slack 重投同一事件，**用户看到重复消息** | ack 写在业务分支**之前**，探针 G12 守顺序 |
| 不校验 `api_app_id` | 同一 app 装在多个 workspace 时，别人的消息进自己的收件箱 | 与 `hello` 里的 `app_id` 比对，不等就丢 |

正文用 `slackTextOf()` 还原：`&amp;` / `&lt;` / `&gt;` 反转义，`<@U123>` → `@U123`，`<#C1|general>` → `#general`。**不查显示名**（要再调 `users.info`）。机器人消息（有 `bot_id`）与系统事件（有 `subtype`）不进收件箱。

### 18.4 Discord Gateway

**要什么**：Bot Token。**intents 里必须有 `MESSAGE_CONTENT`**（`1 << 15`），另外带 `GUILD_MESSAGES`（`1 << 9`）与 `DIRECT_MESSAGES`（`1 << 12`），本项目的组合是 `(1 << 9) | (1 << 12) | (1 << 15)`。

**握手**

```text
GET https://discord.com/api/v10/gateway/bot
Headers: Authorization: Bot <token>
  -> { "url": "wss://gateway.discord.gg" }

连 wss://gateway.discord.gg/?v=10&encoding=json：
<- { "op": 10, "d": { "heartbeat_interval": 41250 } }
-> { "op": 2, "d": { "token": "...", "intents": 33281, "properties": {...} } }
-> { "op": 1, "d": <sequence> }
<- { "op": 11 }
<- { "op": 0, "t": "MESSAGE_CREATE", "s": 7, "d": {...} }
```

**四个坑**

| 坑 | 后果 | 本项目的做法 |
|---|---|---|
| intents 不带 `MESSAGE_CONTENT` | 连接正常、心跳正常、事件也到，**只是 `content` 恒空** | 常量里写死 `1 << 15`，探针 G17 守两个字面量都在 |
| 心跳没被确认还继续挂着 | 半死连接：不报错、不收消息 | 收到 `op:10` 起定时器，上轮没等到 `op:11` 就主动 `close` 让外层重连 |
| 不过滤机器人消息 | 自己推的内容被收回收件箱，再推出去，死循环 | 判 `d.author.bot === true` 直接丢 |
| 想省事做 resume | 要维护 `session_id` + `sequence` + `resume_gateway_url`，状态机复杂 | **不做**：断线整条重连 + 指数退避（2s→4s→…→60s 上限） |

`op:7`（reconnect）与 `op:9`（invalid session）都按「断开重连」处理，不是致命错。

### 18.5 与轮询的对照

| 维度 | 长轮询（Telegram / 微信 / Matrix） | WebSocket（Slack / Discord） | SDK 长连接（飞书） |
|---|---|---|---|
| 谁发起 | 本机 | 本机 | SDK |
| 有游标吗 | 有（`offset` / `get_updates_buf` / `next_batch`） | **没有**，平台推什么收什么 | 由 SDK 管 |
| 断线会丢消息吗 | 不会（游标还在） | **会**（断开期间的事件不补发） | 看 SDK |
| 需要心跳吗 | 不需要 | **需要**（Discord 的 `op:11`） | 由 SDK 管 |
| 需要公网地址 | 不需要 | 不需要 | 不需要 |
| 要代理吗 | 看平台 | **Discord 通常要**（本机实测直连失败） | 看平台 |

「断线会丢消息」是这两个通道与长轮询最本质的差别：v0.19.0 选了「简单重连」而不是 resume，意味着接收进程停一段时间，那段时间的消息**补不回来**。收件箱的定位是记事本，这个取舍是有意的。

### 18.6 加一个新通道时

若那个通道也是 WebSocket，改这几处：

1. `lib/ws.js` 不用动（除非平台要特殊握手）。
2. `lib/receiver.js` 加一个 `{ mode: 'longconn', async run(acc, ctx) }`，返回的 Promise 在 `ctx.signal` abort 或连接断开时 resolve。
3. `WORKERS` 里注册它；`NOT_RECEIVABLE_REASON` 删掉对应那条。
4. 前端 `lib/client.js` 的 `RECEIVE_MODE` 加一行收法文案。
5. `scaffold/probe_receive.mjs` 的 G 段加断言（worker 形态、凭据缺失的本地拒绝、协议里那几条不能写错的字面量）。

## 十九、消息按钮（v0.20.0 新增）

### 19.1 谁支持

| 通道 | 能带按钮 | 协议字段 |
| --- | --- | --- |
| Telegram | ✅ | `reply_markup.inline_keyboard` |
| Slack | ✅ | `blocks[]`（`type: "actions"`） |
| Discord | ✅ | `components[]`（`type: 1` action row） |
| 飞书 | ❌ | 要互动卡片（interactive card） |
| QQ | ❌ | `keyboard` 字段，群与频道格式不同 |
| 微信 | ❌ | iLink 没有按钮消息类型 |
| 钉钉 | ❌ | 只能 markdown / text / link |
| 企业微信 | ❌ | 只能 markdown / text |
| 企业微信自建应用 | ❌ | 要 templates/card 且需申请模板 |
| 群晖 Chat | ❌ | webhook 只收文本与附件 |
| Matrix | ❌ | 要自定义 HTML/组件，客户端支持不一致 |
| 邮件 | ❌ | 邮件不能有按钮，只能写链接 |

判据是「有没有实现按钮翻译」，不是「平台文档里有没有按钮概念」。所以后九个通道**照常发文字**，按钮丢弃并在结果里点名原因。

### 19.2 一种写法

调用方只写这一种（一维数组，自动每 5 个折行）：

```json
[{"text":"通过","callback":"ok"},{"text":"拒绝","callback":"no"}]
```

想显式分行就写二维数组：

```json
[[{"text":"通过","callback":"ok"}], [{"text":"详情","callback":"more"}]]
```

也可以传 JSON 字符串（接口和工具参数都是这种形式）。字段别名：`text` 或 `label`；`callback` 或 `value` 或 `custom_id`。

### 19.3 三条上限，全按最严的那家定

| 上限 | 值 | 出处 |
| --- | --- | --- |
| `callback` 字节数 | 64 | Telegram `CALLBACK_DATA_MAX_BYTES` |
| 按钮总数 | 25 | Slack 单个 `actions` block 上限 |
| 每行个数 | 5 | Discord action row 上限 |

**按字节验，不按字符验**：`"中".repeat(22)` 是 66 字节。

### 19.4 三处实现各自要注意的

**Telegram**（`lib/channels/telegram.js`）
- 空 `inline_keyboard` 是合法的，那是**清键盘**的写法。所以「没有按钮」不能发空数组，得根本不发 `reply_markup`。
- 按钮只挂**最后一块**（`i === blocks.length - 1`）。

**Slack**（`lib/channels/slack.js`）
- `blocks` 与 `text` 同时给时，客户端优先渲染 `blocks`，`text` 退化成通知预览与无障碍朗读 —— 所以 `text` 照传，别以为有 blocks 就不用 text。
- `action_id` 用序号（`dshb_0`、`dshb_1`）而不是按钮文字：文字可能是中文或带空格，进 id 会出问题。回调值放 `value`。

**Discord**（`lib/channels/discord.js`）
- `components` 上限是 5 行 action row、每行 5 个，超了整条 400。折行与总量校验在 `buttons.js` 统一做。
- 按钮 `type: 2` / `style: 2`（Secondary）；回调值放 `custom_id`。

### 19.5 按钮是通道能力，不是消息属性

这是本轮唯一一个「会改变既有行为」的决策点，值得单独写清。

如果按「消息属性」处理 —— 一条消息带了按钮，那所有目标通道都必须支持按钮，否则整批发失败 —— 后果是：给 12 个通道群发带按钮的消息，9 个不支持，整批失败，一条都发不出去。群发功能直接废掉。

所以 `bus.send` 的选择是：不支持的通道**照常把文字发出去**，只在 `detail` 里追加一句

```text
；该通道不支持按钮，按钮已丢弃（要互动卡片 interactive card）
```

判据是 `ok === true` 且 detail 含这句。这样用户能看清「谁带上了、谁没带上、为什么」。

### 19.6 界面

试发页（左侧「试发一条」）多一个输入框：**按钮（可选，JSON）**。下方提示实时显示哪几个通道支持按钮（从 `GET /buttons/channels` 取，不写死在前端）。

试发页的「只看分块（不发）」也会校验按钮格式 —— 坏格式在这一步就报「按钮「X」没有 callback」，不用等真发出去 400。

### 19.7 接口与工具

| 入口 | 用途 |
| --- | --- |
| `GET /buttons/channels` | 回 `{ok, channels, reasons}`，谁支持、其余为什么 |
| `POST /send` 的 `buttons` | 发消息时带按钮 |
| `POST /test` 的 `buttons` | 试发页 |
| 工具 `push_hub_send` 的 `buttons` | 同上，收 JSON 字符串 |

### 19.8 加新通道的按钮支持要改哪几处

1. `lib/buttons.js` 里加一个 `toXxx(rows)` 翻译函数。
2. `buttonsFor()` 里加一条分支；`BUTTON_CHANNELS` 加名字；`NO_BUTTON_REASON` 删掉该通道那条（否则同一通道既「支持」又有「不支持原因」，自相矛盾）。
3. 该通道的 `send()` 里 `parseButtons` → 翻译 → **只挂最后一块**。
4. `scaffold/probe_buttons.mjs` 的 B 段加翻译断言、C 段改数量、D 段加接入断言。

## 二十、QQ 接收：官方网关的裸协议（v0.21.0 新增）

### 20.1 为什么能收

QQ 官方机器人没有「拉取消息」的 HTTP 接口，只有 **WebSocket 网关**。但**连接是本机发起的**（`wss://api.sgroup.qq.com/websocket`），所以不需要公网回调地址 —— 与飞书 / Slack / Discord 同一类，而不是与群晖那种「平台回调进来」的同类。

v0.16.0 曾把 QQ 列为收不了，理由是官方 SDK `@tencent-connect/qqbot-nodejs` 在 profile 里装坏了（`ERR_PACKAGE_PATH_NOT_EXPORTED`）。**那个判断错在「没有 SDK 就收不了」**：网关是公开的裸协议，只需知道 `op` 码与地址怎么拿，用本插件自己的 `lib/ws.js` 就能连。飞书不同 —— 它的事件是加密信封（`encrypt` + `verification_token`），必须用官方 SDK 解，所以飞书只能借 profile 的依赖。

### 20.2 握手流程

| 步 | 做什么 | 失败表现 |
|---|---|---|
| 1 | `appToken()` 拿 accessToken（复用发消息那条链路） | 400 或 401；本地缺 appId / clientSecret 时**直接返回，不连出去** |
| 2 | `GET https://api.sgroup.qq.com/gateway`，`Authorization: QQBot <token>` | 裸 token 401，报错只说连不上 |
| 3 | 连 `wss`，等 `op:10` hello，按 `heartbeat_interval` 起心跳 | interval 非法就主动断开 |
| 4 | 发 `op:2 identify`，`d.token` 也要 `QQBot <token>` | 401 关闭 |
| 5 | 收 `op:11` = 心跳确认；没确认就主动断开重连 | 半死连接会挂着不报错但收不到消息 |
| 6 | 收 `op:0` 的 `GROUP_AT_MESSAGE_CREATE` / `C2C_MESSAGE_CREATE` | —— |

### 20.3 intents 与两种事件

```
const QQ_INTENTS = 1 << 25  // GROUP_AND_C2C_EVENT
```

**不带这一位不报错**：连接正常、心跳正常，就是群里 @ 机器人的消息一条都收不到。这与 Discord 缺 `MESSAGE_CONTENT` 的表现不同（那个是事件照来但 `content` 恒为空），排查手感完全两样 —— 前者只能靠「群里 @ 了但收件箱空着」发现。

| 事件 | 触发场景 | `from` 取 |
|---|---|---|
| `GROUP_AT_MESSAGE_CREATE` | 群里 @ 机器人 | `d.group_openid` |
| `C2C_MESSAGE_CREATE` | 单聊 | `d.author.user_openid` |

正文都是 `d.content`（纯字符串，不带 @ 占位）。时间走 `qqTime()`：RFC3339 → ISO，`Date.parse` 拿不准返回 `undefined`，由 `inbox.appendMessage` 填当前时间。

### 20.4 不走 resume

QQ 与 Discord 都支持 `op:6 resume`（带 `session_id` + `sequence` 续传），本插件两个都不做。收件箱是记事本不是审计日志，断几条不致命；resume 要维护两个状态并处理「resume 失败退回 identify」。断了就整条重连，退避 2s→4s→8s…上限 60s。

### 20.5 不做 msg_id 去重

官方文档明确同一条消息可能重复推送。本插件**宁可重复也不漏**：收件箱每条有独立 `id`，重复由下游按内容与时间去判。做去重要维护一张 ID 表并处理过期，收益不抵复杂度。

### 20.6 现在能收 / 收不了

能收 **7 个**：telegram / wechat / feishu / matrix / slack / discord / qq。

收不了 **5 个**：

| 通道 | 原因 |
|---|---|
| synology_chat | 只有「传出 URL」回调，NAS 连不进 127.0.0.1 |
| dingtalk | 群机器人是纯发送 webhook，没有读取接口 |
| wecom | 同上 |
| wecom_app | 自建应用要配「接收消息服务器」回调，宿主没有公网地址 |
| email | 收邮件要 IMAP，与「推送」语义不同 |

```powershell

Invoke-RestMethod "$api/receive/status" | ConvertTo-Json -Depth 4

```

## 二十一、按钮回调接收（v0.22.0 新增）

### 21.1 为什么必须有这一节

v0.20.0 让三个通道能带按钮（Telegram / Slack / Discord），但**按下去之后没人接**。三家的表现不同，共同点是都不报错：

| 通道 | v0.21.0 之前的实际状态 |
|---|---|
| Telegram | `allowed_updates` 只订阅 `message`，`callback_query` 不下发。按下后那条 update 一直留在队列，`offset` 推不动 —— **之后所有消息都收不到**，整条链路静默死掉 |
| Slack | `block_actions` 帧照常推到 Socket Mode，但没有解析分支，被当成不认识的事件忽略 |
| Discord | `INTERACTION_CREATE` 照常推到 Gateway 同样被忽略；且 Discord 要求 3 秒内应答，不应答客户端显示「交互失败」 |

### 21.2 三家怎么接

| 通道 | 事件/订阅 | 回调值 | 应答义务 | 做错的后果 |
|---|---|---|---|---|
| telegram | `allowed_updates: ['message','callback_query']` | `cq.data` | `POST answerCallbackQuery`（`callback_query_id`） | 整条接收链路死掉 / 客户端一直转圈 |
| slack | `event_callback` 内 `event.type === 'block_actions'` | `actions[0].value` | 无需额外应答（`envelope_id` ack 已在 v0.19.0 做掉） | 回调静默丢失 |
| discord | `INTERACTION_CREATE` 且 `d.type === 3` | `d.data.custom_id` | `POST /interactions/{id}/{token}/callback` body `{ type: 6 }` | 客户端显示「交互失败」（3 秒超时） |

### 21.3 三条硬纪律

1. **应答必须在记账之前**。Telegram 先 `answerCallback` 再 `onMessage`；Discord 用 `void answerInteraction(d, acc)` 不等待但同样不能串在落盘之后。先记账后应答的话，记账一抛错客户端就永远转圈。
2. **Slack 取 `action.value` 不是 `action.text`**。`text` 是按钮上显示的字（「确认」「取消」），`value` 才是业务值。取错会把显示文案当业务值处理。
3. **Discord `type` 必须是 `3`**。`2` 是斜杠命令（`APPLICATION_COMMAND`）、`5` 是表单提交（`MODAL_SUBMIT`），都不是按钮，必须跳过 —— 否则会把别的交互当按钮回调塞进收件箱。

### 21.4 收件箱怎么区分

`inbox.json` 每条记录多了可选字段 `kind`：

```json
{
  "id": "telegram-m8x2k1-a3f9c2",
  "channel": "telegram",
  "account": "主号",
  "kind": "callback",
  "at": "2026-11-17T11:20:33.000Z",
  "from": "6317****92",
  "text": "ok",
  "raw": { "callbackId": "4382...", "data": "ok", "messageId": 512, "userId": 6317****92, "userName": "<你>" }
}
```

- 普通消息**没有** `kind` 这个键（不是 `kind: "message"`）。v0.21.0 之前的老文件不用迁移。
- 界面上回调条目左侧一条蓝边 + 一枚「按钮按下」标签 —— 回调的「正文」是 `ok` / `yes` 这种业务值，混在消息里会被误读。
- 只想看回调：`GET /receive/inbox/callbacks` 或工具 `push_hub_receive action=callbacks`。

### 21.5 刻意没做

| 没做 | 理由 |
|---|---|
| 回调自动触发动作 | 一旦插件按回调做事，就要回答「按两次怎么办」「是不是发起人按的」「要不要收键盘」——那是审批卡的复杂度（dsh-im `approval-card.mjs` 的四步：先应答 → 校验 actor → 同步占位防重 → 提交后改消息收键盘）。本插件只负责把回调送到调用方手上 |
| 幂等去重 | Slack 与 Discord 都会重投，同一 `callback_id` 可能在收件箱出现两次。收件箱是记事本不是审计日志 |
| actor 校验 | 谁按到按钮都落进收件箱，不判断是不是发起人。要这个判断由调用方做 |

### 21.6 加新通道的回调支持要改哪几处

1. `lib/receiver.js` 该通道的 worker（轮询型在 `poll` 里加分支，长连接型在帧处理里加分支）
2. `answerXxx()` 应答函数（若平台有应答义务）
3. 落盘时传 `kind: 'callback'`
4. `lib/client.js` 若有新的显示需求，在收件箱 `map` 里加判断
5. `scaffold/probe_receive.mjs` H 段加断言

## 二十二、邮件接收（v0.23.0 新增）

### 22.1 为什么改主意了

v0.15.0 到 v0.22.0 一直把邮件列在「收不了」，理由是「要 IMAP，与推送语义不同」。这个理由经不起推敲：

- **IMAP 同样是本机主动连出去**，与 Telegram 的 `getUpdates`、Matrix 的 `/sync` 没有本质区别，都不需要公网地址、都不需要端口映射。
- **「发出去的通知有人回了邮件」恰恰是推送中枢最该知道的事**。日报发出去、对方回一句「这个数不对」，这条回复比任何群消息都重要。

之前是把「宿主没有公网回调地址」这个真限制扩大解释了。

### 22.2 收发是两套服务器

| | 发信 | 收信 |
|---|---|---|
| 协议 | SMTP | IMAP |
| QQ 邮箱 | `smtp.qq.com:465` | `imap.qq.com:993` |
| 163 邮箱 | `smtp.163.com:465` | `imap.163.com:993` |
| Gmail | `smtp.gmail.com:587` | `imap.gmail.com:993` |

**域名和端口都不一样**。所以机器人卡的邮件通道多了两个字段：`imapHost`（例 `imap.qq.com`）与 `imapPort`（留空 = 993）。两者都是可选的 —— 只发信的用户一个字都不用填；一旦点了「开始接收」，没填 `imapHost` 就直接拒并说清缺的是 IMAP 不是 SMTP。

### 22.3 那个会漏信的写法

想当然的写法：

```js
// ❌ 别这么写
for await (const msg of client.fetch({ seen: false }, { source: true })) {
  if (fetched >= 20) break
  // …处理
}
```

后果是**静默丢信**：`break` 时游标已推到第 20 封，下一轮只查 `uid > 游标`，第 21 封之后的未读落在查询范围外；而 IMAP 在 `fetch` 时默认打上 `\Seen`，那些信在邮箱里也不再是未读 —— **既不在收件箱、也不在未读列表**，用户永远不会知道有这些信。

正确写法：

```js
const uidList = since > 0
  ? await client.search({ uid: String(since + 1) + ':*' }, { uid: true })
  : await client.search({ seen: false }, { uid: true })
// 没有游标时取最新的 20 封；有游标时取最老的 20 封
const picked = (since > 0 ? uidList : uidList.slice(-EMAIL_BATCH)).slice(0, EMAIL_BATCH)
for (const uid of picked) {
  const msg = await client.fetchOne(String(uid), { uid: true, source: true }, { uid: true })
}
```

### 22.4 其余四条要点

| 要点 | 做法 | 不这么做会怎样 |
|---|---|---|
| 无游标只查未读 | `{ seen: false }` | 第一次接入把几千封历史灌进收件箱，上限 500 条把新信挤掉 |
| 加 INBOX 锁 | `getMailboxLock('INBOX')` | 同账号两个循环并发取信会撞，IMAP 断连 |
| 主题拼进正文 | `'【' + subject + '】' + text` | 收件箱一堆没上下文的正文 |
| 自签证书共用开关 | `allowSelfSigned` → `tls.rejectUnauthorized = false` | 同一台自建服务器的信发得出收不进 |

### 22.5 轮询间隔

`EMAIL_POLL_MS = 30_000`，一轮取到东西时**不等 30 秒立刻再来一轮**（可能还有下一批）；取不到才睡。

不做 IMAP `IDLE`：IDLE 要在同一条连接上等服务器推，断线重连、`NOOP` 保活、读信时不能并发取信都得自己兜。30 秒一次短连接对任何邮箱都不算负担。

### 22.6 现在能收 / 收不了

能收 **8 个**：telegram / wechat / feishu / matrix / slack / discord / qq / email。

收不了 **4 个**：synology_chat（只有传出 URL 回调）/ dingtalk（纯发送 webhook）/ wecom（同上）/ wecom_app（要配接收消息服务器回调）。

### 22.7 刻意没做

| 没做 | 理由 |
|---|---|
| IMAP IDLE | 见 22.5 |
| 游标落盘 | `acc.__imapUid` 只在进程内，重启后从头取最近 20 封未读。重复几条不撑爆、不漏，但要精确续传得写进配置文件 |
| 邮件线程归并 | 同一话题来回十几封会变十几条独立消息。归并要 `References`/`In-Reply-To` 加状态机，是 dsh-im 那套对话机器人的活 |
| 附件落盘 | `mailparser` 能拿 Buffer，但落盘路径、去重、清理没设计 |

## 二十三、钉钉 Stream 与企业微信智能机器人（v0.24.0 新增）

v0.23.0 之前，这一栏把钉钉与企业微信写成「收不了」，理由是群机器人是纯发送 webhook。**这句话只是半个事实** —— 两家都有长连接型的收消息通道，只是不叫群机器人。

### 23.1 收发凭据是两套

| 通道 | 发送用什么 | 接收用什么 |
|---|---|---|
| 钉钉 | 群机器人 `webhookUrl` + 加签 `secret` | 企业内部应用的 `clientId`（AppKey）/ `clientSecret`（AppSecret） |
| 企业微信 | 群机器人 `webhookUrl` | 智能机器人的 `botId` / `botSecret` |
| 企业微信（自建应用发送） | `corpId` / `corpSecret` / `agentId` | 仍是智能机器人的 `botId` / `botSecret` |

界面上这四个新字段全带「（接收才要）」后缀。只发消息的人不用填，看到后缀就知道与自己无关。

### 23.2 钉钉：先应答再处理

`dingtalk-stream` 的 `DWClient` 推到本机的每条消息都带 `headers.messageId`，SDK 要求先调 `socketCallBackResponse` 应答，否则钉钉会重投。

```js
client.registerCallbackListener(TOPIC_ROBOT, (response) => {
  const messageId = response?.headers?.messageId
  if (messageId) { try { client.socketCallBackResponse(messageId, { success: true }) } catch {} }
  const message = JSON.parse(response.data)
  if (message?.msgtype !== 'text') return
  onMessage({ from: message.senderStaffId ?? message.senderId, text: message.text.content })
})
```

顺序反了 → 用户收到两条一样的回复。这正是 `probe_receive.mjs` 的 J7 守的那条（用 `lastIndexOf` 定位，因为 `dingtalkTextOf` 的函数定义在 worker 之前）。

话题名用 `TOPIC_ROBOT`（`/v1.0/im/bot/messages/get`）不要手写：拼错的话订阅不上，一条都收不到**且不报错**。

### 23.3 企业微信：智能机器人 WSClient

```js
const { WSClient } = require('@wecom/aibot-node-sdk')
const client = new WSClient({ botId, secret, logger: quiet, maxReconnectAttempts: 10 })
client.on('message', (frame) => {
  const body = frame?.body
  const text = body?.msgtype === 'text' ? body.text.content : body?.msgtype === 'voice' ? body.voice.content : ''
  if (text === '') return
  onMessage({ from: body.chattype === 'group' ? body.chatid : body.from?.userid, text })
})
client.connect()
```

会话归属：群消息按 `body.chatid`、单聊按 `body.from.userid`。语音消息的正文在 `body.voice.content`（平台已转文字），所以也收。

### 23.4 现在能收 / 收不了

能收 **10 个**：telegram / wechat / feishu / matrix / slack / discord / qq / email / dingtalk / wecom_app。

## 二十四、引用回复（v0.25.0 新增）

### 24.1 谁支持、谁不支持

| 通道 | 支持 | 写法 / 原因 |
|---|---|---|
| telegram | ✅ | `reply_parameters: { message_id, allow_sending_without_reply: true }` |
| slack | ✅ | `thread_ts`（**是开线程，不是引用条**） |
| discord | ✅ | `message_reference: { message_id, channel_id, fail_if_not_exists: false }` |
| matrix | ✅ | `content.m.relates_to['m.in_reply_to'].event_id` + 正文 `> 原文` 前缀 |
| qq | ✅ | `msg_id` + `msg_seq`（被动回复有窗口期） |
| feishu | ❌ | 要走 `/messages/:id/reply` 端点，不是发消息加字段 |
| wechat | ❌ | iLink 的消息结构里没有引用字段 |
| dingtalk | ❌ | Stream 只能收，发消息的 `msgtype` 里没有引用类型 |
| wecom | ❌ | 群机器人只能发 markdown/text |
| wecom_app | ❌ | `quote` 参数另有一套语义，且要模板卡片 |
| synology_chat | ❌ | webhook 只收文本与附件 |
| email | ❌ | 有 `In-Reply-To` 头，但本插件发信是「一次性 SMTP」，没有线程状态 |

### 24.2 五家的字段完全不兼容

这是必须做中间层的原因：

```js
// 同一句「回复 12345」，五家要的东西毫无交集
telegram: { reply_parameters: { message_id: '12345', allow_sending_without_reply: true } }
slack:    { thread_ts: '12345' }                        // 注意：改了语义，是开线程
discord:  { message_reference: { message_id: '12345', channel_id: 'C', fail_if_not_exists: false } }
matrix:   { 'm.relates_to': { 'm.in_reply_to': { event_id: '12345' } } }  // 且正文要自己加 > 前缀
qq:       { msg_id: '12345', msg_seq: 1 }
```

所以 `lib/reply.js` 做了一层通道无关的 `replyFor(channel, messageId, extra)`，五个通道实现里只剩一行：

```js
...(replyTo !== '' && last ? replyFor('telegram', replyTo) : {})
```

### 24.3 三个必须做对的点

| 点 | 做法 | 不这么做会怎样 |
|---|---|---|
| 只挂最后一块 | 三处都判 `last`（`i === blocks.length - 1`） | 切成 3 块的长消息带 3 个 `reply_parameters`，同一句被引用三遍；Matrix 的 `> 原文` 前缀拼三遍 |
| Matrix 正文自带前缀 | `matrixQuotePrefix(text, id)` | 引用关系只在 `m.relates_to` 里，客户端不渲染时看着就是一句平白的话 |
| 空 ID 不算「不支持」 | `bus` 里 `undefined` / `null` / 空白串三个都判 | 每次普通发送都在 `detail` 里挂一句「该通道不支持引用回复」，日志全是噪音 |

### 24.4 为什么降级在 bus 层，不下沉到通道

与按钮完全同一条纪律：**回复是「通道能力」不是「消息属性」**。

如果按消息属性处理（带上 `replyTo` 就只发支持回复的通道），用户群发到 12 个通道时会因 7 个不支持而整批失败 —— 群发功能直接废掉。所以 `lib/bus.js` 的处理是：不支持的那 7 个照常把文字发出去，`ok` 仍是 `true`，只在 `detail` 里挂一句「该通道不支持引用回复，这句是当新消息发的（原因）」。

### 24.5 接口与工具

| 入口 | 参数 | 说明 |
|---|---|---|
| `POST /send` | `replyTo` 或 `reply_to` | 群发，不支持的通道降级并点名 |
| `POST /test` | `replyTo` | 试发 |
| `POST /send/account` | 不支持 | 单账号发送走 `bus.sendOne`，接口层没暴露（工具里也没有） |
| `push_hub_send` 工具 | `reply_to` | 与 `dry_run` 同样用下划线 |
| `GET /reply/channels` | — | 回 `{channels, reasons}`，前端拿它渲染提示，不写死 |

伪发送（`dry_run: true`）的返回体里有 `replyTo.droppedChannels` —— 写了 `replyTo` 却群发到 12 个通道时，被丢弃的 7 个在这里点名，不用真发就知道会丢。

### 24.6 加新通道的引用支持要改哪几处

1. `lib/reply.js` 的 `replyFor` 加一个 `case`
2. `lib/reply.js` 的 `REPLY_CHANNELS` 加通道名
3. `lib/reply.js` 的 `NO_REPLY_REASON` **删掉**该通道那一条
4. 该通道的 `send()` 加三处（导入 / 解析 `options.replyTo` / body 里的 `...(replyTo !== '' && last ? replyFor(...) : {})`）
5. `scaffold/probe_reply.mjs` 的 E 段那个数组加一行（它会自动展开成三条断言）

**注意第 3 步最容易漏**：只加 `REPLY_CHANNELS` 不删原因表，界面会同时显示「支持」和「不支持」。

## 二十五、通道显示（v0.26.0 新增）

### 25.1 一个界面偏好，不是功能开关

`channel_visibility` 只决定**设置界面左侧列表显示哪些通道**。它不参与发送、不参与接收、不参与默认推送的解析。

> 隐藏一个通道 ≠ 停用它。

代码层的硬线：这个键只被 `lib/client.js` 读，`lib/bus.js` 与 `lib/receiver.js` **一个字都不读**。可以用两行 `grep` 自证：

```bash
grep -c "channel_visibility" lib/bus.js        # 必须 0
grep -c "channel_visibility" lib/receiver.js   # 必须 0
```

### 25.2 配置形状

```json
{
  "channel_visibility": {
    "mode": "all",
    "hidden": ["wecom", "wecom_app"]
  }
}
```

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `mode` | `"all"` / `"bound"` | `"all"` | `all`=全部列出；`bound`=只列有账号的 |
| `hidden` | string[] | `[]` | 手动关掉的通道名 |

两档**叠加**：先按 mode 决定基础集合，再减 hidden。

### 25.3 归一化：写错只会「多显示」

`lib/config.js` 的 `channelVisibility(cfg)`：

| 输入 | 输出 | 为什么这么处理 |
|---|---|---|
| 无 `channel_visibility` | `{mode:'all',hidden:[]}` | 没配过 = 全显示 |
| `mode: "Bound"` | `mode:'all'` | 只认小写 `bound`，写错一律回落「全显示」 |
| `mode: 123` / `null` | `mode:'all'` | 同上 |
| `hidden: "wecom"` | `hidden:[]` | 不是数组就当没写 |
| `hidden: ['wecom','乱写','wecom']` | `hidden:['wecom']` | 剔除未知通道名 + 去重 |

**写错方向是「多显示」而不是「少显示」** —— 手滑不会把通道弄丢。

### 25.4 三道过滤的顺序不能反

```js
// 1. 存在哪些通道
const channelKeys = Object.keys(ownFields).length > 0 ? Object.keys(ownFields) : CHANNEL_ORDER
// 2. mode==='bound' 只留有账号的；3. 最后减 hidden
const visibleChannelKeys = channelKeys.filter((channel) => {
  if (hiddenSet.has(channel)) return false                                   // 3
  if (visMode === 'bound' && accountCountOf(channel) === 0) return false     // 2
  return true
})
```

顺序反了会出这个 bug：用户手动隐藏一条「本来就没账号」的通道 → hidden 把它去掉 → 但 bound 模式的判定与它重叠 → 用户切回 `all` 时它**冒出来**（因为 hidden 的判定已经被 mode 的判定吃掉了）。注释里的原话：

> 第 3 步必须在最后：用户手动隐藏一条「本来就没账号」的通道时，顺序反了会让它在 bound 模式下又冒出来。

### 25.5 账号数只许有一个算法

左栏「3 个账号 / 未配置」与「通道显示」页里的同一句话，必须走同一个 `accountCountOf()`：

```js
const accountCountOf = (channel) => {
  const info = channels.find((c) => String(c?.name) === channel)
  const fromServer = Array.isArray(info?.accounts) ? info.accounts.length : -1
  return fromServer >= 0 ? fromServer : ownRows(channel).length
}
```

优先后端落盘真值（`/config` 返回的 `channels[].accounts.length`），取不到回落本地 `ownRows`（刚加账号还没 reload 的那一瞬间）。两处各写一份会让同一通道在两页显示不同数字。

### 25.6 两处兜底

| 场景 | 兜底 | 不做的后果 |
|---|---|---|
| 当前选中的通道被隐藏 | `effectiveSelected` 落到第一个可见通道 | 右侧渲染一个左侧不存在的通道，像卡住 |
| 全部通道被隐藏 | 左栏与右侧各给一句专门说明 | 两侧都空白，用户以为插件坏了 |

### 25.7 不许用 filter 实现隐藏

最省事的写法 `setChannels((prev) => prev.filter(...))` 会连带污染：账号数统计、「代发通道」页清单、`buildPayload` 的 `picked`、默认推送校验。**一个纯界面偏好绝不能改配置本身**。探针 F3 专门禁止这个写法。

### 25.8 界面怎么用

2. 顶部两档二选一：**全部显示** / **只显示已配置的**
3. 下面十二行逐通道勾「显示」；关掉的会带「已隐藏」徽章并说明原因（手动隐藏 / 被 bound 自动藏）

## 二十六、设置面板滚动（v0.26.1 新增）

### 26.1 现象：看起来像「内容只有半截」

主人从左上角点开设置面板后，工具区只到「扫码接入」，下面五项（试发一条 / 代理通道 / 接收消息 / 通道显示 / 通道来源）一个都看不见，也没有滚动条。

判断这件事的第一条线索：**页面看起来「干净地结束」了**。

| 观感 | 更可能是 |
|---|---|
| 有空白、有「读取中…」、有红色横幅 | 数据没回来 / 请求失败 |
| 内容完整、样式正常，但到某一行就没了 | **被容器裁掉**（滚动问题） |
| 整块都不显示、控制台报错 | JS 崩溃 / 组件没挂载 |

第二条线索：**有没有滚动条**。插件根节点如果没有声明高度，它「以为」自己有足够空间，浏览器不会给它滚动条；而宿主容器有定高，超出的部分直接被裁。两边都不知道对方在干什么，结果就是内容消失。

### 26.2 根因

`.dph-root` 原样式只有色板变量、`box-sizing`、`padding`、字体与颜色，**没有高度也没有 overflow**。

```css
/* 修复前 */
.dph-root {
  --dph-blue: ...;
  box-sizing: border-box;
  padding: 2px 0 24px;
  color: var(--dph-label-1);
  font-size: 13px;
  line-height: 1.55;
}
```

宿主那边（`settings.section` / 侧栏面板）给的是定高容器。于是：

1. `.dph-root` 高度 = auto = 内容高度（可能是 1200px）；
2. 容器高度 = 100% = 视口高度（比如 800px）；
3. 两者不一致时，容器按自己的 overflow 处理 —— 默认是裁；
4. `.dph-root` 自己没声明 `overflow`，不产生滚动条。

**问题不在「内容没渲染」，在「高度从哪来」。**

### 26.3 修法：三样缺一都不成立

```css
/* 修复后 */
.dph-root {
  ...
  height: 100%;
  min-height: 0;
  padding: 2px 0 28px;
  overflow-y: auto;
  overflow-x: hidden;
  overscroll-behavior: contain;
  scrollbar-gutter: stable;
}
```

| 声明 | 漏了会怎样 | 为什么 |
|---|---|---|
| `height: 100%` | 根节点高度仍由内容决定，宿主直接裁掉溢出，永远不出滚动条 | 需要先有一个「我不能更高」的约束，浏览器才知道该滚 |
| `overflow-y: auto` | 高度被钉死成容器高，但超出部分是**裁**不是**滚**，用户看到的还是一半 | height 只给边界，overflow 决定越界怎么办 |
| `min-height: 0` | 作为 grid/flex 子项时默认 `min-height: auto`，会被内容顶到比 `height` 更大，滚动条不出现 | 这是最隐蔽的一条；`min-height: auto` 的语义是「不能比内容更矮」 |

### 26.4 两条体验项

| 声明 | 少了会怎样 |
|---|---|
| `scrollbar-gutter: stable` | 滚动条一出现/消失，内容左右横跳一下（窄面板上特别明显）。提前预留槽位就没这个抖动 |
| `overscroll-behavior: contain` | 滚到底时把手势传递给外层页面，用户想滚面板结果整页跟着动 |

因为 `scrollbar-gutter` 已经在右侧预留了槽位，**不能再加 `padding-right`** —— 否则内容离右边缘会出现双份空隙。这就是 `padding` 保持 `2px 0 28px`（左右 0）的原因；底部从 24 提到 28 是给最后一行留呼吸。

### 26.5 刻意不用的两种写法

**不用 `max-height: 100vh` / `height: 100vh`**。`vh` 参照的是**视口**，不是容器。宿主把设置面板嵌在侧边抽屉或分栏里时，`100vh` 会算出比实际可用高度大得多的高度 —— 要么滚动条永远不出来（把容器撑开），要么出现比容器更大的一页。

**不用 `position: fixed`**。已确认 `lib/theme.js` 里 `position: absolute` / `sticky` / `fixed` / `z-index` **0 命中**，页面没有浮层，不存在「overflow 把浮层裁掉」的风险。

⚠️ 如果将来要加浮层（下拉菜单、气泡提示），记住一条：**`overflow: auto` 的祖先会裁掉 `position: absolute` 的后代**。那时浮层要么 portal 到 `body`，要么改用 `position: fixed`，否则会被裁在面板边界上。

### 26.6 两份 CSS 必须一起改

`lib/theme.js` 导出 `THEME_CSS`，`lib/client.js` 里又内联了一份同名常量 —— 因为 ModuleLoader 只能 `require` 宿主给的模块，不能 `import` 相对路径，所以只能各写一份。

**只改一份的后果是「探针绿但界面没变」**：`lib/theme.js` 那份在浏览器里根本不生效，实际注入的是 `lib/client.js` 里那份。

```bash

node scaffold/probe_scroll.mjs
```

C1 逐字节比对两份，C3 额外确认内联那份也带滚动声明。

v0.26.1 的实测同源结果：`len=25171` / `hash=75b81801` / `same=true`。

### 26.7 探针守什么

`scaffold/probe_scroll.mjs`，**13 项断言**（`SCROLL_OK`）：

| 段 | 项数 | 守什么 |
|---|---|---|
| A | 6 | 根节点规则块找得到、有 `height: 100%` / `overflow-y: auto` / `overflow-x: hidden` / `box-sizing: border-box` / `overscroll-behavior: contain` |

## 二十七、删账号（v0.26.2 新增）

### 27.1 现象与判别

主人反馈：「QQ账号我已经移除，再进去的时候为什么还在？其他通道看看是不是也有这个问题。」

三个特征可以对号入座：

| 现象 | 是不是本缺陷 |
|---|---|
| 界面上删掉一条账号，那条立刻消失，但刷新后回来了 | **是**。删除在前端生效（React state 变了），落盘被后端忽略 |
| 删掉一条后刷新什么都没变（原来几条还几条） | 不是。这是整体保存失败，看 `/api/config` 的返回 |
| 删掉后界面不消失，还弹报错 | 不是。这是前端 save 失败，通常 4xx/5xx |
| 只有 QQ 有问题，别的通道正常 | **不是**。本次缺陷十二个通道同路径，只是你先删的是 QQ |

### 27.2 根因：一个词的两种理解

`own_bots` 是**以通道名为键的对象**。合并时「这个键不存在」有两种可能的意思：

1. 「这次没提到这个通道」（局部提交、老前端）—— 应该**保留**磁盘上的值。
2. 「我把这个通道清空了」—— 应该**删掉**磁盘上的值。

后端选了 1，前端删除时表达的却是 2，于是删除动作在落盘环节蒸发。

```js
// 后端 lib/index.js
const own = { ...oldOwn }                                    // 起点是磁盘旧值
for (const [channel, fields] of Object.entries(OWN_BOT_FIELDS)) {
  if (!Object.hasOwn(incomingOwn, channel)) continue          // ① 没提到 → 保留
  ...
  if (accounts.length === 0) delete own[channel]              // ② 空数组 → 删掉
  else own[channel] = accounts
}
```

分支 ② 一直写着，但前端从来不送空数组（它送的是「没有这个键」），所以 ② 从来没被执行过 —— **死代码**。

### 27.3 约定

| 前端提交的形状 | 后端理解 | 磁盘结果 |
|---|---|---|
| 没有 `qq` 键 | 这次没提到 qq | 保留旧账号 |
| `{ qq: [] }` | 明确清空 qq | 删掉整个 qq 键 |
| `{ qq: [{...}] }` | 设置 / 更新 qq | 落盘一行或多行 |

**空数组 ≠ 没提到**。这是本插件对外的一条接口约定，命令行调用 `/api/config` 也适用：想删一个通道的账号，传空数组，不要省略该键。

### 27.4 修法

```js
// 前端 lib/client.js
const dropOwn = (channel, index) => {
  setOwnBots((prev) => {
    const list = (Array.isArray(prev?.[channel]) ? prev[channel] : []).filter((_, i) => i !== index)
    return { ...prev, [channel]: list }   // 空数组 = 明确「这个通道我一条都不剩了」
  })
}
```

只在删空时改行为，删到还有剩时语义不变（还是那几条，只是少了被删的那条）。**没有改后端**：分支 ② 本来就在，现在终于被走到。

### 27.5 为什么不能反过来「删掉后端的 continue」

看到 `if (!Object.hasOwn(incomingOwn, channel)) continue` 第一反应是「就是它保住了旧账号」。不能删：

1. 命令行与脚本只提交要改的通道（例如 `{own_bots:{telegram:[...]}}`），删了 `continue` 会把其它十一个通道全清空。
2. 升级过程中并发打开的旧标签页提交的 payload 不含新通道，同理。
3. 「只改一个通道」是常态，把它变成「每次必须提交全部通道」是接口设计的倒退。

正确做法是让前端把「删空」表达清楚，而不是让后端猜。

### 27.6 加新通道时注意

新增一个自有机器人通道只需在 `OWN_BOT_FIELDS` 里加一项 —— 合并、掩码、删除**全部自动**走同一条 `for (const [channel, fields] of Object.entries(OWN_BOT_FIELDS))`。**不要**给它单独写合并分支，也不要给它单独写删除入口。

## 二十八、入站附件（v0.27.0 新增）

### 28.1 这个洞是怎么来的

v0.27.0 之前，十个接收通道里每一个都是这样取正文的：

```
const text = String(msg?.text ?? '')
if (text.trim() === '') continue
```

Telegram 发来一张图，事件里没有 `text`；发来一个 PDF，也没有 `text`；发来一段语音，还是没有。于是全部 `continue` 掉 —— 收件箱里一个字都没有。用户以为插件坏了，实际消息早就收到了。

这不是「某个通道漏了」，是**九个通道全都漏了，漏的方式一模一样**：把一个「有没有文字」的判据，当成了「有没有消息」的判据。

Slack 另外还有一处独立的硬伤：`if (message.subtype !== undefined) return` 把 `file_share`（发文件时的 subtype）一起挡掉了，等于「Slack 发来的文件永远收不到」。

### 28.2 十个平台各自的形状

| 通道 | 附件字段 | 反直觉的地方 |
|---|---|---|
| Telegram | `message.photo[]` / `document` / `voice` / `audio` | `photo[]` 是**同一张图的多档分辨率**，不是多张图 |
| Slack | `event.files[]` | 发文件时 `subtype === 'file_share'` |
| Discord | `message.attachments[]` | 字段名是 `filename` / `content_type`（下划线），不是 `name` / `mimetype` |
| Matrix | `content.msgtype` = `m.image`/`m.file`/`m.audio`/`m.video` | **`content.body` 在这里是文件名，不是正文** |
| 飞书 | `message.content`（按 `message_type`） | `content` 是 **JSON 字符串**，要先 `JSON.parse` |
| QQ | `d.attachments[]` | **5 分钟窗口**，过了取不到 |
| 钉钉 | `msgtype` = picture/file/audio | picture **只给 `downloadCode`，没有文件名** |
| 企微智能机器人 | `body.mixed.msg_item[]` | 推不了文件与图片，只有 mixed 可能带 |
| 邮件 | `parsed.attachments[]` | 内联图片也在里面 |

### 28.3 归一化后的统一形状

```
{ kind: 'image' | 'file' | 'voice', name: 'photo-a1b2.jpg', mediaType: 'image/jpeg', size: 921600 }
```

- `kindOf(name, mediaType)`：**mime 优先于扩展名**。`.bin` 配 `image/png` 应该算图片。
- `humanSize(bytes)`：拿不到体积时返回**空串**，不写「0 B」—— 那会让人以为真的是 0 字节。
- `summarize(list)`：→ `[图片 photo-a1b2.jpg 900.0 KB]`，多个用空格连。
- `compact()`：跳过空项、补「(未命名)」、截 10 条。

### 28.4 三个必须做对的点

**① 正文空判定要连着附件一起判。**
旧：`if (text.trim() === '') continue` → 「只发了张图、没配文字」整条丢掉。
新：`if (caption.trim() === '' && attachments.length === 0) return` → 两者同时为空才拒。

**② 摘要拼在正文里，但只能拼一次。**
后端 `deliver` 里拼；前端只渲染 `msg.text`。两边都拼会出现「[图片 x.jpg] [图片 x.jpg]」。

**③ 上限在两层都要有。**
`compact()` 里 `slice(0, 10)`，`inbox.appendMessage` 里也 `slice(0, 10)` —— 前者防一个事件带 50 个附件撑爆一条消息，后者防手工写入绕过。

### 28.5 为什么只记不下载

拉附件要处理：单文件上限（Telegram 20MB / Discord 25MB）、落盘路径、清理策略、凭据泄漏（Slack 的 `url_private` 自带 token，落盘就等于把 token 写进文件系统）。

这几件事加起来是另一个量级的功能，硬塞进这一版只会做坏。而「谁在什么时候给我发了个什么文件」这件事，**记录本身就已经解决了大半问题**。

## 二十九、发送回执（v0.28.0 新增）

### 29.1 为什么先做这一件

「改消息 / 撤回 / 表情」三件事都要先回答同一个问题：**我要动的那条，在平台上是哪一条？** 而 v0.28.0 之前，十二个通道的 `send()` 一律只回 `{ ok: true, detail: '已发送 N 块（…）' }` —— 消息发得出去，**id 一个都没留**。所以不是那三件没实现，是**地基一直缺着**。

### 29.2 十二家谁给得出 id

| 通道 | 字段 | 给得出 |
|---|---|---|
| Telegram | `data.result.message_id` | ✅ |
| Slack | `data.ts` | ✅ |
| Discord | `data.id`（顶层） | ✅ |
| Matrix | `data.event_id` | ✅ |
| 飞书 | `data.message_id` | ✅ |
| QQ | 回包 `.id`（先 `parseJson`） | ✅ |
| 邮件 | `info.messageId` | ✅ |
| 微信 | `{ ret, errcode }` | ❌ |
| 群晖 | `{ success }` | ❌ |
| 钉钉 | `{ errcode }` | ❌ |
| 企业微信群机器人 | `{ errcode }` | ❌ |
| 企业微信智能机器人 | `{ errcode }` | ❌ |

给不出的五家是**平台层面没有消息 id 概念**，不是插件没去取。这一版对它们**不编造** —— 探针里反过来断言这五个文件里不许出现 `messageIds`。

### 29.3 发件箱的形状

存 `~/.dsh/dsh-push-hub/outbox.json`：

```json
{
  "version": 1,
  "updatedAt": "2026-11-17T21:17:47.236Z",
  "messages": [
    {
      "id": "sent-20261117211747-nkzq8c",
      "at": "2026-11-17T21:17:47.236Z",
      "channel": "telegram",
      "account": "主号",
      "target": "-100123",
      "kind": "text",
      "text": "端到端自检",
      "messageIds": ["9001", "9002"],
      "detail": "ok"
    }
  ]
}
```

- `MAX_KEEP = 500`：超了截 `slice(-500)`，挤掉最老的
- `TEXT_CLIP = 200`：正文折叠空白后截 200 字，超了加 `…`
- **原子替换**：先写 `outbox.json.tmp-<pid>` 再 `rename` —— 写一半断电不会留下半个文件
- **mode `0o600`**：里面有聊天位置，不该被同机其他用户读到

### 29.4 `messageIds` 为什么是数组，不是字符串

长消息会按各平台上限**分块**发送。**每一块在平台上都是一条独立消息，各有自己的 id。**

- 只留最后一个 → 「改第一条」时找不到它
- 只留第一个 → 「改最后一条」时找不到它

所以 `messageIds: string[]`，且**逐块 push**，不是循环结束后取最后一次。

多目标还要**逐目标挂**：`deliveries[].messageIds` 与摊平的总数组并存。只留摊平的，就分不清哪个 id 属于哪个聊天 —— 「把 A 群那条改掉」会打到 B 群去。

### 29.5 两条「不做」的纪律

| 不做 | 为什么 |
|---|---|
| **失败不进发件箱** | 失败的消息**没有 id**，记进去既不能改也不能撤，只会把真发出去的挤出 500 条窗口。判据是逐条 `if (one?.ok !== true) continue`，不是看整批 `ok` |
| **记账失败不改 `ok`** | 消息确实发出去了。写盘失败只是「没留痕」，不能反过来说「没发成功」——那会让人重发一遍，造成重复消息 |

### 29.6 接口与工具

| 入口 | 说明 |
|---|---|
| `GET /api/send/history?limit=N` | 返回 `{ ok, path, count, entries }`，新的在前 |
| 工具 `push_hub_sent` | `action=recent`（看记录，可 `limit` / `channel` 过滤）/ `action=path`（文件在哪） |

工具的返回值里 `withIds` **单独数出来** —— 免得看到 `count: 40` 就以为四十条都能改。

▲ **查历史必须走 `readQuery(req)`**：`req.url` 在 `lib/index.js` 里是**字符串**（`const url = String(req.url ?? '')`），对它调 `url.searchParams.get()` 会在运行时崩 `TypeError: Cannot read properties of undefined (reading 'get')`。

### 29.7 界面

左侧「工具」区多一项 **发送记录**。每条：

- 通道中文名 + 「文字 / 文件」标签 + 账号 + 时间 + 正文摘要
- 末行二选一：`消息 id：9001、9002`（绿边，能改能撤）／`这个通道的回包不给消息 id —— 这条以后改不了也撤不回。`

### 29.8 给新通道加回执要改哪几处

1. `lib/channels/<新通道>.js` 的 `send()` 里 `const ids = []`，循环里把回包 id push 进去，返回对象加 `messageIds: ids`。
2. **平台给不出 id 就别加** —— 让 `messageIds` 保持不存在，探针会断言这一点，比编一个假 id 强。
3. `lib/bus.js` 的三处 `sendToTargets` 分支已通用，不用改（它读 `outcome?.messageIds`）。
4. `lib/index.js` 的 `doSend` 记账循环也通用，不用改。
5. 在 `scaffold/probe_outbox.mjs` 的 B 段加一条：要么断言有 `messageIds`，要么断言没有。

## 三十、改消息与撤回（v0.29.0 新增）

### 30.1 能力边界：四家做得了，八家做不了

| 通道 | 改 | 撤 | 凭什么 |
|---|---|---|---|
| telegram | ✅ | ✅ | `editMessageText` / `deleteMessage`，dsh-im 有现成实现 |
| slack | ✅ | ✅ | `chat.update`（dsh-im 有）/ `chat.delete`（dsh-im 没有，按官方文档补） |
| discord | ✅ | ✅ | PATCH / DELETE `/channels/:cid/messages/:mid`（PATCH dsh-im 有，DELETE 按文档补） |
| matrix | ✅ | ✅ | `m.replace` 新事件 / `redact` |
| feishu | ❌ | ❌ | 官方文档有，但**本机无凭据实测**、抓文档只回 25 字节、社区有 `invalid msg_type` —— 不做 |
| qq / email / wechat / dingtalk / wecom / wecom_app / synology_chat | ❌ | ❌ | 平台没有对应接口，或（邮件）投递后不可撤回 |

飞书这条要理解成**纪律**而不是遗漏：「宁可没有，也不要一个按下去必然报错的按钮」。

### 30.2 四家的协议差异

```text
telegram  POST  /bot<token>/editMessageText   { chat_id, message_id, text, disable_web_page_preview:true }
          POST  /bot<token>/deleteMessage     { chat_id, message_id }

slack     POST  https://slack.com/api/chat.update   { channel, ts, text }
          POST  https://slack.com/api/chat.delete   { channel, ts }

discord   PATCH  https://discord.com/api/v10/channels/<cid>/messages/<mid>
                 { content, allowed_mentions:{ parse:[], replied_user:false } }
          DELETE 同路径（成功 204，响应体为空）

matrix    PUT   /rooms/<rid>/send/m.room.message/<txn>
                 { msgtype:"m.text", body:"* "+新正文,
                   "m.new_content":{ msgtype:"m.text", body:新正文 },
                   "m.relates_to":{ event_id:<原事件>, rel_type:"m.replace" } }
          PUT   /rooms/<rid>/redact/<eid>/<txn>   {}
```

注意 Matrix 的「改」**不是编辑原事件**：原文还在，客户端看到 `m.replace` 关系才把新事件显示成「原文被改过」。撤回是不可逆的 `redact`，但客户端可能还留着本地缓存 —— 文案里写明了这一点。

### 30.3 三个必须做对

| 细节 | 不做会怎样 |
|---|---|
| Telegram `message is not modified` 判成功 | 改成一样的字会报「改失败」，但实际已经是目标状态 |
| Discord 改消息带 `allowed_mentions:{parse:[]}` | 改完正文带 `@everyone` 会真 ping 全频道 |
| Discord 撤回判 `204/200` 不看 body | 204 响应体为空，按 body 判会把成功判成失败 |

跨四家的两条：

- **改消息不许分块**（`send()` 会切块，`editMessage()` 不能 —— 拆成两条就成了「原来 A，现在 B 和 C」）。
- **空正文本地拒**（那是「撤回」的语义，不是「编辑」）。

### 30.4 位置从哪来

统一：`chatId` 优先，回落 `targetOf(acc).id`。判断式：

```js
const chatId = String(options?.chatId ?? "").trim() !== ""
  ? String(options.chatId).trim()
  : (target === null ? "" : target.id)
```

为什么优先 `chatId`：发件箱里存着**当时那条消息发去的目标**，比「现在这个账号的默认目标」准（用户可能改过配置）。

### 30.5 发件箱的 `places` 分组（补 v0.28.0 缺口）

```json
{ "channel": "telegram", "account": "主号", "target": "聊天A、聊天B",
  "places": [ { "id": "聊天A", "messageIds": ["101","102"] },
              { "id": "聊天B", "messageIds": ["201","202"] } ],
  "messageIds": ["101","102","201","202"] }
```

老条目（没有 `places`）：单值 `target` 能反查；多目标 join 的字符串返回空数组 —— **定位不了就不猜**。

### 30.6 接口与工具

| 入口 | 说明 |
|---|---|
| `GET /edit/channels` | `{ok, edit:[4], del:[4], editReasons:{8}, deleteReasons:{8}}` |
| `POST /send/edit` | `{channel, messageId, text, account?, chatId?}`（驼峰与下划线都认），失败 502 |
| `POST /send/delete` | `{channel, messageId, account?, chatId?}` |
| 工具 `push_hub_edit` / `push_hub_delete` | 同上，返回 JSON 化结果 |

1. `lib/edits.js` 的 `EDIT_CHANNELS` / `DELETE_CHANNELS` 加名字，并从 `NO_EDIT_REASON` / `NO_DELETE_REASON` 里删掉它那条（探针会断言「能做的通道不应有原因」「不能做的通道必须有原因」）。

## 三十一、表情回应（v0.30.0 新增）

### 31.1 一句话

给发出去的那条消息挂一个表情（reaction），四个通道能做：telegram / slack / discord / matrix。

### 31.2 四家的形状没有一处相同

| 家 | 请求形状 | 语义陷阱 |
|---|---|---|
| Telegram | `POST /bot<token>/setMessageReaction`，body `{chat_id, message_id, reaction: [{type:'emoji', emoji:'👍'}]}` | **`reaction: []` = 清掉全部**。它没有「只删某一个」的接口 |
| Slack | `POST /api/reactions.add`（去是 `reactions.remove`），body `{channel, timestamp, name}` | **`name` 要名字不要字符**；传 `👍` 回 `invalid_name` 而 **HTTP 仍是 200** |
| Discord | `PUT /channels/:cid/messages/:mid/reactions/<emoji>/@me`（去是 DELETE） | 成功是 **204 且响应体为空**；自定义表情必须 `name:id` |
| Matrix | PUT `/rooms/:rid/send/m.reaction/:txn`，content `{'m.relates_to':{event_id,rel_type:'m.annotation'},'m.reaction':key}` | 表情是**一个独立事件**；「去掉」要撤回那个事件，收的是**回应事件 id** 不是原消息 id |

**Slack 那条是本版最阴的**：失败发生在业务层（`{"ok":false,"error":"invalid_name"}`）而 HTTP 层成功（200）。只判 `res.ok` 的代码会把它当成功，用户看到「点了、提示成功了、表情没出来」。

### 31.3 Slack 名字表的纪律：宁可拒绝，不猜

`lib/reactions.js` 的 `slackNameOf(emoji)`：

1. 纯 ASCII 名字（`thumbsup` / `rocket`）**原样放行** —— 用户已经填对了。
2. `+1` → `thumbsup`、`-1` → `thumbsdown`（Slack 自己的别名）。
3. Unicode 查一张 **34 个常用表情** 的常量表（👍→thumbsup、🎉→tada、❤️→heart、😂→joy、🚀→rocket ……）。
4. **表里没有的返回 ok:false**，文案：

> Slack 认的是表情名字（例如 thumbsup），不是这个字符。这个表情不在内置对照表里，请直接填 Slack 的名字，别填 emoji。

**为什么不猜**：猜错名字比不映射更糟。不映射时用户知道「这个要我自己填名字」；猜错时用户会以为「这个表情 Slack 不支持」，然后在别处继续碰壁。Slack 的表情名字表有几千个，内置 34 个只是最常见的，硬猜等于编造。

### 31.4 调度顺序（bus.addReaction）

顺序不是随手排的，每一步拦的东西不同：

```
1. normalizeChannel         → 通道名不认识
2. reactionBlocker(name)    → 平台没有这个能力（八家）
3. 空 messageId             → 「发件箱里那条没有 id 就加不了表情」
4. normalizeEmoji(emoji)    → 空 / 超 64 字符（多半是把正文当表情了）
5. slackNameOf（仅 slack）  → 名字表里没有，让用户填名字
6. account(cfg, name, input.account) → 找不到账号
7. typeof mod.addReaction === 'function'
8. 真调用，try/catch
```

**第 5 步必须排在找账号之前**：名字填错是调用方错误，不该因为「刚好没配 Slack 账号」被掩盖成「没有账号」—— 那样用户会去配账号，配完还是错。

## 三十二、依赖解析（v0.31.0 新增）

### 32.1 一句话

第三方依赖从哪来，收敛到 `lib/deps.js` 一处：**先查插件自己的 `node_modules`，再回落 DSH profile**。

### 32.2 为什么要有这一节

v0.31.0 之前，「借依赖」这件事在四个文件里各写了一遍：

| 文件 | 原来自己写的 |

### 32.3 两级查找：顺序不能反

```
depCandidates() = 去重([                          
  <插件根>/node_modules,          ① 插件自身（优先）
  $DSH_PROFILE_DIR/node_modules,  ② 环境变量指定的 profile
  ~/.dsh/profiles/desktop/node_modules,   ③
  ~/.dsh/profiles/web/node_modules,       ③
  ~/.dsh/profiles/cli/node_modules,       ③
])
```

**为什么插件自身必须排第一**：反过来的话，用户在插件目录 `npm install` 装好了，解析时却先撞上 profile 里那个「碰巧还在、但版本不同」的包 —— 装了等于白装，而且现象是「明明装了还是不生效」，极难查。

去重那一步不能省：`$DSH_PROFILE_DIR` 在 desktop profile 里通常就指向 `~/.dsh/profiles/desktop`，不去重会白跑一遍并且让探针的候选数断言失效。

### 32.4 四个导出，各管一类调用方

| 导出 | 返回 | 谁用 | 为什么是这个形状 |
|---|---|---|---|
| `loadDep(name)` | `{ok, mod, from, via}` / `{ok:false, error}` | 扫码、能力表 | 要把「找不到」渲染成界面提示，不能抛 |

### 32.5 两个坑（都是实际踩到的）

**坑一：`createRequire` 的锚点不能拿 `package.json` 当存在性判据。**

```js
// 错误：候选目录本身就是 node_modules，npm 不在它根下写 package.json
const anchor = path.join(dir, "package.json")
if (!existsSync(anchor)) continue           // ← 全部落空

// 正确
if (!existsSync(dir)) continue
const anchor = path.join(dir, "noop.js")    // 文件不必存在，只用它所在目录
```

症状是「装了 52 个包、却报找不到依赖」。这种 bug 不会报错，只会静默跳过每一个候选。

**坑二：纯 ESM 包让 `req.resolve()` 抛 `ERR_PACKAGE_PATH_NOT_EXPORTED`。**

`@tencent-connect/qqbot-nodejs@1.0.4` 的 `exports`：

```json
{ ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" } }
```

只有 `import`，没有 `require` 也没有 `default`。这种包**装着头在，但 require 不进来**。解法是 catch 里退回按目录直查，再走动态 `import()`：

```js
try { entry = req.resolve(specifier) }
catch (resolveError) {
  const direct = path.join(dir, specifier)
  if (!existsSync(path.join(direct, "package.json"))) throw resolveError
  entry = path.join(direct, "package.json")
}
```

### 32.6 包声明纪律

```json
"dependencies": { "@larksuiteoapi/node-sdk": "1.76.0" }
```

| 纪律 | 为什么 |
|---|---|
| **版本钉死，不带 `^`** | `registerApp` 是 1.76 才有的；带 `^` 会被自动升到不兼容的次版本 |
| **只声明这一个** | `react` / `@deepseek-ai/*` 必须用宿主那份，装成本地副本会让 client 端出现两份 React |
| **`node_modules` 不提交** | `.gitignore` 已含 `node_modules/` 与 `version/*/node_modules/` |
| **`package-lock.json` 要提交** | 保证别人装到同一棵依赖树（52 个传递依赖，版本飘一个就可能不兼容） |

### 32.7 加新依赖时改哪几处

1. `package.json` 的 `dependencies` 加**精确版本**。
2. 插件目录 `npm install --legacy-peer-deps --save-exact <name>@<ver>`（`--legacy-peer-deps` 因为 react 那些 peer 在宿主里，本地没有）。
3. 用 `loadDep` / `tryRequire` / `requireDep` 去取 —— **不要再写 `createRequire`**（`probe_deps.mjs` 的 D2/D5/D7/D9 会红）。

## 三十三、流式可编辑消息（v0.32.0 新增）

### 33.1 一句话

一条消息先发出去，之后边想边改它；想完了把剩下的内容接着发。用户不用盯着空白等，也不会被一条长回答刷屏。

### 33.2 为什么做这一节

v0.28.0 有了发件箱（发出去的东西有据可查），v0.29.0 有了改消息与撤回（发出去之后能改），但**发送过程中那一段是空的**：

| 阶段 | 之前 | v0.32.0 之后 |
|---|---|---|
| 发送前 | 什么都没有 | 先发一条「正在处理…」 |
| 发送中 | 什么都没有，等它全想完 | 边想边改这条消息 |
| 发送后 | outbox 有据可查，edits 能改能撤 | 同左 |

dsh-im 早就有这块 —— `src/channels/shared/editable-message-stream.mjs`（**100 行**）。这次的实现等价，不是照抄：它的接口是 `create(initialText)` / `edit(messageId, text)` / `sendRemainder(chunk)` 三个回调，我们这边多一层「能力表 + 账号解析 + 代理注入」，所以分成 `lib/stream.js`（纯逻辑，无 IO）与 `lib/bus.js`（调度，知道账号与代理）两层。

### 33.3 只有四个通道能流

`STREAM_CHANNELS` 是 `Object.freeze([...EDIT_CHANNELS])` —— **从能改的清单派生，不另抄一份**。能流的前提就是能改：流的每一步都是一次 edit。

| 通道 | 能流 | 原因 |
|---|---|---|
| telegram | 能 | `editMessageText` |
| slack | 能 | `chat.update` |
| discord | 能 | `PATCH messages/:id` |
| matrix | 能 | 发 `m.replace` 新事件（不是编辑原事件） |
| feishu | 不能 | 官方有 PATCH 接口，但本机无凭据实测过参数形态（同 v0.29.0 的判断） |
| qq / wechat / synology_chat / dingtalk / wecom / wecom_app | 不能 | 平台没有改消息接口 |
| email | 不能 | 邮件发出去就到对方信箱了，没有「改一封已经投递的邮件」这回事 |

### 33.4 四条纪律（每一条都对应一个真实会踩的坑）

**纪律一：必须节流。** 平台对编辑同一条消息有频控（Telegram 约 1 次/秒/聊天，Slack `chat.update` 是 Tier 3）。每来一个字就 edit 必然被限流，**限流后界面停在半句话上，比不流式更难看**。

**纪律二：同一时刻只有一个 edit 在飞。** 上一条没回就发下一条，回来的顺序不保证；后发先到会让界面**退回**旧文本然后卡住。所以所有 edit 走一条 Promise 链：

```js
function enqueue(task) {
  chain = chain.then(task).catch(err => {
    failures.push({ at: Date.now(), detail: String(err?.message ?? err).slice(0, 200) })
  })
}
```

**纪律三：中途失败不能中断流。** 只记账（`failures` 数组）继续收更新，定稿时再试。一次 edit 失败就整条流作废，等于把「已经想出来的内容」也一起丢了。

**纪律四：finish 必须幂等。** 第二次调用原样返回第一次结果，不重复发余块。否则调用方重试一次就会多出一串重复消息。

### 33.5 分块：只编辑首块

`planChunks(splitter, text, limit)` 返回 `{ first, rest }`。流的过程中只把 `first` 塞进被编辑那条（`[0] ?? initialText`），`rest` 攒着，`finish` 时逐块发。

切法由调用方注入 —— bus 传的是 `lib/text.js` 的 `splitBlocks`。**不能各写一份**：流的时候用一种切法、定稿的时候用另一种，会出现「编辑到一半突然跳到别的地方」。

| 通道 | MAX_CHARS | 说明 |
|---|---|---|
| telegram | 4096 | 官方上限 |
| slack | 3800 | 官方 4000，留 200 给富文本转换 |
| discord | 1900 | 官方 2000，留 100 |
| matrix | 30000 | 最大的一个 |

### 33.6 五个 API、五条路由、三个工具

| 总线导出 | 作用 |
|---|---|
| `openStream(cfg, { channel, account, initialText, intervalMs, chatId })` | 发首条、登记一条流，返回 `streamId` 与 `messageId` |
| `updateStream(streamId, text)` | 送一份进度（合并刷新，不是立刻发） |
| `finishStream(streamId, text)` | 定稿：改首块 + 发余块，然后从活动列表摘掉 |
| `cancelStream(streamId)` | 放弃流（**已发那条留在那里不删**，删是 deleteMessage 的语义） |

| 路由 | 方法 |
|---|---|
| `/send/stream/list` | GET |

| `/send/stream/finish` | POST |

工具：`push_hub_stream_open` / `push_hub_stream_update` / `push_hub_stream_finish`（工具总数 10 → 13）。

### 33.7 两个上限与一个刻意不做的决定

| 常量 | 值 | 为什么 |
|---|---|---|
| `MAX_ACTIVE_STREAMS` | 64 | 满了返回「同时最多 64 条流，先把不用的 finish 或 cancel 掉（当前 N 条）」，不是静默拒绝 |
| `STREAM_TTL_MS` | 30 分钟 | 超时的流由 `sweep()` 掐掉 |
| `MIN_INTERVAL_MS` / `MAX_INTERVAL_MS` | 300 / 10000 | 夹值**必回 detail**，不静默改用户给的值 |

**刻意不做：本模块不开定时器。** `sweep()` 要调用方择机调。理由是不想在宿主进程里留一个永不停的心跳 —— 那个心跳会一直存在，即使一条流都没有。代价是：开了一条流却永远不 finish，它会一直占着一个名额到进程重启。

### 33.8 加新通道要改哪几处

1. 通道能改消息（有 `editMessage` 导出）→ 自动进 `STREAM_CHANNELS`，**不用改 stream.js**。
2. 通道不能改 → 在 `lib/edits.js` 的 `NO_EDIT_REASON` 里写清平台级原因，`NO_STREAM_REASON` 会自动继承。
3. 只有 email 那种「能发但不能改」的特殊语义才需要在 `NO_STREAM_REASON` 里单独覆盖。
4. 在 `scaffold/probe_stream.mjs` 的 A 段加一条能力断言。

## 三十四、进度表情（v0.33.0 新增）

### 34.1 一句话

一条消息发出去之后，先在它上面挂一个「进行中」的表情，跑完换成成功或失败 —— 用户不用翻记录就知道这条任务到哪一步了。

能挂的是 **telegram / slack / discord / matrix** 四家。PROGRESS_CHANNELS 从 REACTION_CHANNELS 派生，不另抄一份名单：能挂进度符号的前提就是能给这条消息加表情。

### 34.2 为什么要有这一节

在 v0.33.0 之前，一条消息的可见生命周期只有两端：发送前能 dry_run 看分块，发送后什么都没有。中间那段「发出去了、正在跑、但你看不出它在跑」是空档 —— 用户只能盯着一条静止的消息猜。

dsh-im 这边对应的是 channels/shared/status-reaction.mjs（109 行，只导出 beginStatusReaction）。本插件按同一套语义实现，但把状态机独立成 lib/progress.js，理由见 34.3。

### 34.3 为什么不塞进 lib/reactions.js

| 关注点 | lib/reactions.js | lib/progress.js |
|---|---|---|
| 管什么 | 「给一条消息加 / 去一个表情」这一件事 | 「一个状态机」：当前挂着什么、要不要先摘再挂、终态只能进一次 |
| 失败语义 | 失败就说失败 | **失败必须吞掉**，不能污染发送结果 |
| 复杂度 | 一次调用 | transition 链 + 幂等 + 记账 + 超时 |

两件事的复杂度不在一个量级。混在一起的结果是 reactions 那层被状态机的复杂度拖着走，或者状态机被 reactions 的「一次调用」假设限制住。

### 34.4 三条纪律

**① best-effort，绝不影响发送结果。** lib/bus.js 里 beginProgress 失败时只在结果加 progressId 空串与 progressDetail，base.ok 原样保留。把「加表情失败」升级成「发送失败」的后果是用户以为没发出去然后重发 —— 对方收到两条。

**② 同一时刻只有一条 transition 在飞。** 换表情是两步（先摘旧、再挂新），并发会出现「旧的摘了新的没挂上」或「同时挂两个」。所有 transition 走一条 Promise 链（chain = chain.then(...)）。

**③ 终态只能进一次。** 第二次 finish 原样返回第一次的 closedResult，一次 provider 调用都不发。调用方重试是常态，来回改表情比根本不挂更糟。

### 34.5 导出表

| 导出 | 返回 | 谁用 | 为什么是这个形状 |
|---|---|---|---|
| PROGRESS_CHANNELS | readonly string[] | bus / index / client | Object.freeze([...REACTION_CHANNELS]) —— 派生，不另抄 |
| PROGRESS_TIMEOUT_MS | 2000 | 状态机内部 | 单次 provider 调用最多等 2 秒，超时当失败继续走，不卡整条链 |
| DEFAULT_EMOJI | {processing: ⏳, success: ✅, error: ❌} | normalizeEmojiSet | Unicode，四家里三家直接用 |
| DEFAULT_SLACK | {hourglass_flowing_sand, white_check_mark, x} | normalizeEmojiSet | **Slack 认名字不认字符**，必须单独一套 |
| NO_PROGRESS_REASON | Record<string, string> | bus / index / client | 8 条平台级原因，界面靠它决定哪些通道不给按钮 |
| canProgress(name) | boolean | 各处判断 | 一句话判据 |
| progressBlocker(name) | string（能挂时为空） | bus | 与 edits / reactions / stream 同一套约定：空串表示能做 |
| normalizeEmojiSet(input, channel) | {ok, emojis, detail} | bus | Slack 走 slackNameOf，表外回落默认 + 说明，**不猜名字** |
| createProgress(opts) | 状态机对象 | bus | addReaction / removeReaction 从参数注入，本文件不碰网络 |

### 34.6 调度顺序（beginProgress 的八步）

1. normalizeChannel → 空通道直接拒
2. progressBlocker(name) → 非空就拒（八家各给平台级原因）
3. 空 messageId 拒 —— 文案是「要给消息 id —— 发件箱里那条没有 id 就挂不了进度表情」
4. account(cfg, name, input.account) → 找不到就拒（区分「该通道没有任何账号」与「没有名为 X 的账号」）
5. normalizeEmojiSet(input.emojis, name) → Slack 在这里翻译成名字
6. 生成 progressId：pg + Date.now().toString(36) + 连字符 + counter.toString(36)
7. createProgress({messageId, emojis, addReaction, removeReaction}) 并塞进 PROGRESS_HUB
8. await machine.start() → 返回时带 progressId 与当前 emoji

**第 3 步在第 4 步之前是有意的**：空 id 是调用方的错，账号是配置的错。先报配置错会把真正的错盖住。

### 34.7 outcome 三种取值

| 传什么 | 挂什么 | 语义 |
|---|---|---|
| success | ✅ / white_check_mark | 任务成功 |
| error 或不传 | ❌ / x | 任务失败 |
| null | 什么都不留（只摘 ⏳） | 这条消息不该带任何状态 |

「不传」当失败、「传 null」当清空 —— 不能合并。

### 34.8 加新通道改哪几处

1. 在 lib/reactions.js 的 REACTION_CHANNELS 里加名字（PROGRESS_CHANNELS 会自动跟上，**不要**去 progress.js 里改）。
2. 在 lib/reactions.js 的 NO_REACTION_REASON 里删掉那家的原因（NO_PROGRESS_REASON 用展开继承，会自动消失）。
3. 该通道的 addReaction / removeReaction 在 v0.30.0 就写好了，不用动。
4. 跑 node scaffold/probe_reactions.mjs 与 node scaffold/probe_progress.mjs —— 后者 A3 会断言两份名单完全一致。

| Telegram 默认表情没实测 | ⏳ ✅ ❌ 不一定都在它的 reaction 集里。挂不上会记进 failures 并在 detail 里说明，不影响消息。 |
| progressId 只在进程内 | 重启后老 id 失效，endProgress 回「没有这条进度」。跨重启收尾要落盘，本轮没做。 |
| 只给首块挂 | 长消息分块后只有第一块带符号。 |
| 状态机不碰网络 | 探针能纯本地跑完；代价是「某通道到底支不支持某个表情」只有真发一次才知道。 |

## 三十五、进度表治理：TTL 与落盘（v0.34.0 新增）

### 35.1 一句话

进度表情挂上去之后，**超时的自己清掉、上限到了说清楚、进程重启过还能收尾** —— 三条治理各管一件事，都写在 lib/progressstore.js 与 lib/bus.js 的进度板块里。

### 35.2 为什么要有这一节

v0.33.0 做完进度表情，三条漏洞是**运行时证据**摆出来的，不是推演：

| 漏洞 | 证据（实测） | 后果 |
|---|---|---|
| 挂上去的不会自己消失 | /send/progress/list 上真挂着 pgmwm27iit-1 / telegram / messageId 999999 / status running / emoji 空串 / errors 1 | 忘了 end 的那条，用户看到一条永远「在跑」的消息 |
| 表只增不减 | lib/bus.js:1025 是 new Map()，唯一的 delete 在 endProgress 里 | 挂够 64 条就再也挂不上，只能重启进程 |
| 重启即失忆 | 进度只活在内存 Map 里，磁盘上什么都没有 | 重启前挂的 ⏳ 永远摘不掉，连 id 都查不到 |

第三条在 v0.33.0 的「已知边界」里就写着「要跨重启收尾得把进度表落盘」—— 等于自己留了坑。这一版填它。

### 35.3 TTL 是 30 分钟，和流式同一个数

| 常量 | 值 | 为什么是这个数 |
|---|---|---|
| PROGRESS_TTL_MS | 30 * 60 * 1000 | 与 lib/stream.js 的 STREAM_TTL_MS 同数。这两个东西描述的是同一种情况：一条长任务最多跑多久。半小时还没收尾的真实含义是**调用方忘了**，不是「任务还在跑」 |
| MAX_ACTIVE_PROGRESS | 64 | 探测阈值不是性能上限。正常用不到两位数，能堆到 64 说明有东西在漏。撞上限的文案直接点明这件事 |
| MAX_KEEP | 200 | 落盘文件最多留多少条。与 outbox 的 500 不同：进度是**待办**不是历史，200 已经远超正常量 |

### 35.4 清理用纯函数算，不开定时器

```js
export function expiredIds(records, ttlMs = PROGRESS_TTL_MS, now = Date.now()) {
  const edge = now - (Number.isFinite(ttlMs) ? ttlMs : PROGRESS_TTL_MS)
  const out = []
  for (const one of Array.isArray(records) ? records : []) {
    const at = Number(one?.createdAt)
    if (!Number.isFinite(at) || at <= 0) continue   // 没有时间的不算超时：宁可留着，不可误删
    if (at < edge) out.push(String(one.id))
  }
  return out
}
```

三个参数全可注入（records / ttlMs / now），探针用固定时钟 NOW = 1700000000000 就能测完三条分支：超时被掐、没超时不掐、没有 createdAt 的不算超时。**为什么不 setInterval**：真开定时器的后果是既测不了（要真等 30 分钟）、又得管生命周期（进程退出前要 clear，忘了就泄漏）。

清理时机沿用 v0.33.0 给流式定的规矩 —— **读列表时顺手清**。listProgress() 与 beginProgress() 都先 sweepProgress()：前者的意思是「你看到的数字就是清理后的真实数字」，后者是为了挂新的一条之前先把位置腾出来。

### 35.5 落盘解决的是收尾，不是「状态机复活」

必须先把话说清楚，否则调用方会误判能力：progress.json 落的是**待办清单**，不是完整状态。跨重启能恢复的只有「这条还挂着、id 是什么、该摘哪个表情」；恢复不了的是**凭据**与**中间 transition 计数**。

所以恢复出来的状态机，两个注入函数都是这样：

```js
createProgress({
  messageId: one.messageId,
  emojis,
  initialEmoji: one.emoji,          // 关键：直接就是 running，不会再挂一次
  addReaction: async () => ({ ok: false, detail: 进程重启过，缺账号凭据… }),
  removeReaction: async () => ({ ok: false, detail: 进程重启过，缺账号凭据… }),
})
```

endProgress 对这类条目会在 detail 里补一句「这条是重启前挂的，凭据已失效，只能按记录摘」。**不假装能恢复得和没重启一样** —— 那会让调用方以为重启后还能正常换表情，然后收到一串失败的 failures。

### 35.6 initialEmoji 为什么不能省

恢复时如果按默认走（status 从 new 起步），finish 的语义是「挂成功表情」，于是平台上会先留着原来那个 ⏳、再挂一个 ✅ —— **一条消息两个符号**。

传了 initialEmoji 之后，状态机一上来就是 running 且 current 就是它，finish 走的是「先摘旧的、再挂新的」，符号数始终是一个。这条与 v0.33.0 的 transition 是同一个机制，但**触发路径完全不同**（一个来自正常 start、一个来自磁盘恢复），所以恢复路径必须单独测 —— 探针 J 段查的就是 restored 后 status 是 running 且 emoji 是 P。

### 35.7 五个导出 + 一次缓存栅栏

| 导出 | 返回 | 谁用 |
|---|---|---|
| MAX_KEEP = 200 | 数字 | 落盘文件最多留多少条 |
| PROGRESS_PATH | 绝对路径 | ~/.dsh/dsh-push-hub/progress.json |
| readProgressStore(filePath?) | {ok, records, detail} | 读坏 / 不存在 / 结构不对一律回空表，**永不抛** |
| writeProgressStore(records, filePath?) | {ok, detail} | mkdir -p → 写 .tmp-<pid>（mode 0o600）→ rename 原子替换 |
| upsertRecord / removeRecord | 新数组 | 纯函数，不改入参 |

**DSH_PUSH_HUB_PROGRESS_PATH** 环境变量可以覆盖路径。两个用处：探针跑测试不污染真实文件；这是唯一能让「重启」在同一个进程里被测出来的办法（见 35.8）。

### 35.8 一个实际踩到的坑：单次栅栏让跨重启路径测不到

ensureProgressRestored() 用 restoredOnce 做栅栏，只读一次盘 —— 这是对的，每次挂表情都读一遍盘是白费。但它带来一个副作用：**同进程里第二次调用不会再读**，而探针与被测代码本来就跑在同一个进程里，于是「重启后恢复」这条路径永远返回 size 0。

第一版真跑就是这么挂的：

```js
// 错误：写完文件再 list，读到的是第一次的缓存（空）
await writeProgressStore([rec], file)
console.log((await bus.listProgress()).size)   // 0 —— 看起来像恢复功能坏了
```

修法是加一个只给测试用的钩子：

```js
export function __resetProgressCache() {   // 双下划线，与 receiver.js 的 __test 同一套约定
  PROGRESS_HUB.clear(); PROGRESS_RECORDS = []; restoredOnce = null; progressCounter = 0
}
```

教训比这个 bug 本身重要：**任何「只做一次」的缓存都必须配一个测试钩子**，否则依赖它的分支在自动化里就是不可达的。真实进程不需要这个钩子 —— 重启天然就是新进程。

### 35.9 listProgress 变 async，三处调用点

| 位置 | 改动 |
|---|---|
| lib/index.js 路由 /send/progress/list | sendJson(res, 200, await bus.listProgress()) |
| lib/index.js 工具 push_hub_progress_list | JSON.stringify(await bus.listProgress(), null, 2) |
| scaffold/probe_progress.mjs E4 | const e4 = await bus.listProgress() |

返回体多了三个字段：swept（这次顺手清掉的 id 数组）、maxActive（64）、以及每条 item 上的 restored 与 ttlMs。界面据此显示「，**重启前挂的**」与「，还有 N 分钟会被自动清掉」。

### 35.11 加新东西时改哪几处

1. 新的进度相关常量放 lib/progress.js（TTL / 上限这类），不要散到 bus.js 里 —— 探针查的就是 progress.js 的导出。
2. 新的落盘字段要同时改三处：recordOf() 造快照、ensureProgressRestored() 读回、readProgressStore 的校验。漏一处就会出现「写进去读不出来」或「读出来是 undefined」。
3. 新的返回字段要同步改三处调用点（路由 / 工具 / 探针），listProgress 是 async，三处都得 await。
4. 任何新的「只读一次」缓存，配一个 __reset 钩子，并在探针里用它模拟重启 —— 否则那条路径测不到。

### 35.12 已知边界

| 边界 | 说明 |
|---|---|
| 重启后只能摘、不能挂 | 凭据不在内存里，恢复出来的状态机 addReaction 恒回失败。endProgress 能把它从记录里清掉，但清不掉平台上那个符号 —— 得人工去删，或者等平台自己过期（Telegram 的表情不会过期）。 |
| 中间计数不跨重启 | stats.updates / stats.edits 重启后从 0 起算。这份文件是待办不是历史，历史在 outbox。 |
| 落盘失败不重试 | writeProgressStore 出错只把 detail 拼进返回，不排队重试。磁盘满的时候进度表会丢，重启后那些符号摘不掉。 |
| MAX_KEEP 200 会截断 | 超过 200 条时保留最近 200 条（slice(-200)）。正常用不到两位数，真撞上说明有东西在大规模泄漏 —— 这时候丢老记录反而是对的。 |


## 三十六、每分钟发送配额（v0.35.0 新增）

### 36.1 一句话

每个「通道 + 账号 + 目标」组合，一分钟内最多发 `perMinute` 块（默认 15，填 0 = 不限）；超了就让调用方等，等到能发为止。

### 36.2 为什么不能靠 chunkDelayMs

| 手段 | 管的是什么 | 在什么场景下无效 |
|---|---|---|
| `chunkDelayMs`（v0.17.0） | 同一批块之间的间隔 | 短消息（每次只有一块）—— 一次都不触发 |
| `perMinute`（v0.35.0） | 一分钟内最多发几块 | 块与块之间隔多久（那是 chunkDelayMs 的事） |

「连着调 20 次 push_hub_send，每次一句话」是**最常见的用法**，而在这个用法里 `chunkDelayMs` 完全不起作用。这是这一节存在的理由：不是「再加一层保险」，而是补一个现有旋钮**在逻辑上无法覆盖**的维度。

### 36.3 三条纪律

写进 `lib/ratelimit.js` 头注释，每条都对应一个真会踩的坑。

**① 限流只让请求变慢，不让它失败。** 超配额的正解是等。真等不了（单次要等超过 60 秒）才报失败，而且**一块都不发** —— 发一半比不发更糟：用户既没收到完整内容，又白耗了配额，还得自己判断「到底发出去多少」。

**② 计数单位是「块」，不是「一次 send 调用」。** 切 5 块就是 5 次 API 调用。按调用计数会**低估 5 倍** —— 这是这一版最容易写错的地方。

**③ 预约制不是检查制。**

```js
// 检查制（错）：两个请求同时进，都看到「还有空位」，然后一起发
if (used < perMinute) { used += 1; send() }

// 预约制（对）：槽位一压到未来就算用掉，后来的人看到的是压完之后的数
const at = now() + waitMs
for (let i = 0; i < want; i += 1) slots.push(at)
```

检查制的 bug **只在并发下出现**，本地一个人测永远测不出来。

### 36.4 配额怎么填

| 填什么 | 结果 | detail |
|---|---|---|
| 留空 / 空串 | 默认 15 条/分钟 | 空（不啰嗦） |
| `0` | **不限**，一次都不等 | 「该账号不限每分钟条数（填 0 即关闭）」 |
| `1`~`30` | 就是它 | 空 |
| `>30` | 夹到 30 | 「…真想关掉请填 0」 |
| 负数 / 非数字 | 回落 15 | 如实说「负数」「不是数字」 |

两条不能省：**0 与「留空」必须是两种语义**（留空 = 用默认，0 = 明确关掉）；**任何夹值 / 回落都要回 `detail`**（静默改用户给的值会骗人）。

`mergeUserConfig` 对 `perMinute` 要特判 `>= 0`：既有的数字分支是 `n > 0` 才写入，填 0 会被当成「没填」静默丢掉，看着像 bug。

### 36.5 闸门放哪、桶键怎么算

闸门 `gatedSend(mod, body, acc, options)` 只有一份，被 `sendToTargets` 的三支扇出全走一遍：

| 分支 | 调用形状 |
|---|---|
| 零目标 | `await gatedSend(mod, body, acc, effective)` |
| 单目标 | `await gatedSend(mod, body, { ...acc, target: targets[0] }, effective)` |
| 多目标 | `await gatedSend(mod, body, { ...acc, target: t }, effective)` |

**为什么不写在四个调用方**（send / sendOne / 流式开流 / 流式补发）里：多写三处必然漏一处，漏的那一处平时不报错，只在被限流时才暴露 —— 那时候已经晚了。

桶键必须是三元组：

```js
// 错：同一个机器人往两个群发，两个群各有各的配额，合成一个桶会互相顶
const bucketKey = channel

// 对：通道 | 账号 | 目标
const bucketKey = channel + '|' + String(acc?.name ?? '') + '|' + String(acc?.target?.id ?? '')
```

合成一个桶的后果：A 群刚发满 15 条，B 群明明一条没发也要跟着等 —— 用户看到的是「换个群发也被卡住」，完全找不到原因。

### 36.6 一个必现的 bug：配额 1 却切了 20 块

```js
// 错误：want > perMinute 时 overflow 必然大于 slots.length，取到 undefined
const overflow = slots.length + want - perMinute
const bottleneck = slots[overflow - 1]
waitMs = Math.max(0, Math.round(bottleneck + windowMs - now()))   // NaN
```

症状是 `take(20)` 返回 `{ ok: true, waitMs: NaN }` —— 调用方 `sleep(NaN)` 立刻返回（等于没等），于是**在超配额的情况下照发不误**。这是「限流器自己把限流放开了」，比不装更糟：装了就以为有保护。

修法见 `lib/ratelimit.js` 里算 `waitMs` 之前那段 `if (want > perMinute)` 分支：切 20 块而配额 1 条，等多久都发不完，**如实拒比让调用方干等 20 分钟更诚实**。

### 36.7 刻意不落盘、刻意不清桶

- 限流窗口只有 60 秒，落盘再读回来的收益近乎为零；
- 落盘会让「重启」变成一次绕过限流的机会，反而更危险；
- 写盘失败要不要判发送失败？判了就是「磁盘满导致消息发不出去」，不判就是白写一次盘。不值得。

同理 `LIMITERS` 不主动清桶：清空窗口等于偷偷放宽限流。桶随进程结束消失，这就够了。

### 36.8 接口、字段与页面

| 类型 | 名字 | 说明 |
|---|---|---|
| 路由 | `GET /send/limits` | `{ ok, defaults, reasons, channels, buckets, size }` |
| 工具 | `push_hub_limits` | 同上，第 17 个工具 |
| 账号字段 | `perMinute` | 高级分组，`type: 'number'`，placeholder 写明 0 = 不限 |
| 页面 | 设置页「发送配额」 | 只读：哪些通道适用、默认多少、各桶已用几条 |

`buckets` 每项形状 `{ key, perMinute, used, waits, blocked }`，键是 `通道|账号|目标`。桶只在第一次发送时创建 —— 没发过的目标不会出现，这不是遗漏。

### 36.9 加新通道或新发送入口时改哪几处

1. 通道模块本身**不用改**：闸门在 `lib/bus.js` 的 `sendToTargets` 之上，与通道实现无关。
2. 新通道如果要豁免限流，在 `lib/ratelimit.js` 的 `NO_LIMIT_REASON` 里加一行（目前只有 email）。
3. 新的发送入口**一律走 `sendToTargets`**，不要自己调 `mod.send` —— 绕过去就没有闸门了。`probe_ratelimit.mjs` 的 F 段会断言三支扇出的调用形状。
4. 改桶键必须同步改 `scaffold/probe_ratelimit.mjs` 的 G 段（它按 `key` 查桶）。

### 36.11 已知边界

| 边界 | 说明 |
|---|---|
| **30 条/分钟不是平台真实上限** | 是本插件愿意跑的最快速度。Telegram 真实配额按聊天算且随账号权重浮动，写死「官方值」反而误导。 |
| **只在同一进程内计数** | 重启清空（正确行为，见 36.7）。多进程部署会各自记账，合起来仍可能超平台配额。 |
| **email 不适用** | 一次 send 就是一封且不分块，平台限制的是每天几百封这种量级。用每分钟配额卡它反而会挡住正常日报。 |
| **超配额时阻塞调用方** | `sleep` 在请求链路里，工具调用最长会慢 60 秒，不是后台排队。没有队列，也不打算加。 |
| **桶只在第一次发送时创建** | 没发过的目标不出现在 `/send/limits` 里。 |


## 三十七、入站附件下载（v0.36.0 新增）

### 37.1 一句话

对方发来的图片 / 文件 / 语音，真的落到本机 `~/.dsh/dsh-push-hub/files/<日期>/`，不再是收件箱里一行文字。

### 37.2 为什么 v0.27.0 只记不取

v0.27.0 的 `lib/attachments.js` 头注释写死了立场：

> **刻意不做下载**：拉附件要处理单个文件上限、落盘路径、清理策略、凭据泄漏（Slack 的 url_private 带 token），这些是另一个量级的事。本轮只做「记录」。

这四条这一版全做了。但真正拦住的不是它们，是第五件当时没注意的事：**句柄被丢了**。

旧的 `compact()`（`lib/attachments.js:63` 附近）只保留 `{kind,name,mediaType,size}`，Telegram 的 `file_id`、Slack 的 `url_private_download`、Discord 的 `url`、Matrix 的 `mxc://…`、飞书的 `file_key` 一个都没留 —— 等到想下载时手上只有文件名。所以这一版第一件事是把句柄留下来。

### 37.3 handle 的形状

| type | 关键字段 | 秘密怎么处理 |
|---|---|---|
| `telegram` | `fileId` `fileName` | file_id 不是凭据；token 下载时现取 |
| `slack` | `id` `fileName` | `url_private_download` **被剥掉**，用 `acc.botToken` 重拼 |
| `discord` | `id` `fileName` | `url` **被剥掉**（限时签名） |
| `matrix` | `mxc` `fileName` | `mxc://` 是资源坐标不是凭据；accessToken 现取 |
| `feishu` | `messageId` + `fileKey`/`imageKey` + `kind` | tenant token 现换 |
| `email` | `buffer` | 不走网络 |
| `none` | `reason` | 取不到（平台不给，或本轮没做 —— 见 37.4） |

`safeHandle()` 只留白名单键，再补 `downloadable: true|false`。`isDownloadable()` 收的是 **handle 对象不是裸字符串**（`isDownloadable('telegram') === false`）。

### 37.4 两条铁律

**不落盘秘密**：`appendMessage` 会把 attachments 原样写进 `inbox.json`，凡留在 handle 里最终都是硬盘明文。Slack 的 `url_private_download` 严格说不是凭据（token 要另放 Authorization 头），但它是「无需鉴权就能定位到哪个 workspace 哪个文件」的串，而 `inbox.json` 是会被发给别人做排障的东西。Discord 的 CDN 签名四小时有效。钉钉的 `downloadCode` 一次性。**能重新算出来的就不要存。**

**取不到就如实标记**：QQ（5 分钟窗口内要主动拉）／钉钉（要拿 downloadCode 换临时 URL）／企微智能机器人（链路本身不给文件）走 `{type:'none',reason}`。界面显示具体原因而不是笼统的「下载失败」—— 重试一万次没用，跟「过一会儿可以重试」是两回事，混在一起用户会以为网络不稳。

**措辞上不用「平台不给」**，因为它对 QQ 与钉钉不是事实：这两家**平台是给接口的**，只是本轮没做（QQ 只有 5 分钟窗口、钉钉要换一次性票据，都会明显拖长这一版）。只有企微智能机器人是真的链路不给。`NO_DOWNLOAD_REASON` 因此写「这条本轮没做，所以取不到」，既不夸大平台限制，也不用「暂不支持」敷衍。

### 37.5 三条纪律（lib/download.js 头注释）

1. **下载失败不影响收消息** —— `downloadAll()` 逐条吞异常，最坏全带 `download.state='failed'` 落盘，消息本体一个字不少。
2. **上限在传输层生效不是事后检查** —— `saveAttachment` 先比声明的 `item.size`，超限一个字节都不请求；`lib/http.js` 的 `viaProxy` 边收边累加、一超 `maxBytes` 就 `response.destroy()`。
3. **落盘文件名不信任平台** —— `safeName()` 洗 `\ / : * ? " < > |` 与控制符、折叠 `..`、去前导点、截 120 字。

### 37.6 三个策略点

放**配置顶层**（`config.DOWNLOAD_KEY = 'download'`），不放账号层 —— 是「本机硬盘怎么用」不是「某个通道的偏好」。

| 键 | 默认 | 范围 | 0 的含义 |
|---|---|---|---|
| `maxFileMB` | 10 | 0–200 | 不限 |
| `retainDays` | 7 | 0–365 | 不按天数清 |
| `maxTotalMB` | 200 | 0–10240 | 不限总量 |

三种语义不合并：留空 → 默认；`0` → 明确关闭；数字 → 夹值且**夹值必回 detail**。合法值（含 0）`detail` 恒空。

```text
normalizeMaxFileMB('abc')   -> { value: 10, detail: '单文件上限「abc」不是有效数字，已按默认 10 MB 处理。' }
normalizeRetainDays(-1)     -> { value: 7,  detail: '保留天数「-1」不是有效数字，已按默认 7 天处理。' }
```

### 37.7 两轮清理

第一轮按 `retainDays` 删过期，第二轮按 `maxTotalMB` 从最老的删到不超限。

只做天数：一天收 500 MB，七天 3.5 GB，天数管不住。只做总量：十年前那个 1 KB 小文件也会被当垃圾清掉，因为它最老。两轮一起才完整。删完顺手清空日期目录。两个值填 0 时对应那一轮直接跳过。

### 37.8 五平台取文件（+ 邮件为何不走网络）

```text
telegram : POST .../bot<token>/getFile {file_id} -> result.file_path
           GET  .../file/bot<token>/<file_path>
slack    : GET  url_private_download  + header authorization: Bearer <botToken>
discord  : GET  cdn.discordapp.com 签名 URL（不需鉴权头）
matrix   : mxc://server/mediaid -> <homeserver>/_matrix/media/v3/download/server/mediaid?allow_redirect=true
           + header authorization: Bearer <accessToken>
feishu   : POST open-apis/auth/v3/tenant_access_token/internal {app_id,app_secret}
           GET  open-apis/im/v1/messages/<message_id>/resources/<file_key>?type=image|file
email    : parsed.attachments[].content 已是 Buffer，不走网络
```

`file_id` **不是 URL**，必须两步。Slack 漏了 Bearer 会拿到 200 + HTML 登录页（不是 401，得看 content-type）。Matrix 的 `allow_redirect=true` 不能漏，否则很多 homeserver 只回 302 不跟。

**决策：飞书 token 自己换，不导出 `lib/channels/feishu.js:52` 的私有 `tenantToken()`** —— 导它会让 channels/feishu.js 承担「给 download 用」的额外职责，而这里只有一个 POST，不值得动别人的导出面。

### 37.9 下载在接收链路里的位置

`lib/receiver.js` 的 `deliver(row)` 里，下载在 `appendMessage` **之前**：

```js
const withFiles = attachments.length === 0 ? attachments : await downloadAll(attachments, acc, policyOf())
appendMessage({ channel, account, from, text, at, kind, attachments: forStore(withFiles), raw })
```

记录一旦写下去这条消息就「已完成」，补下载得靠人回来点，而用户不会回来点。`policyOf()` 每次重读配置不缓存（改完立刻生效），读失败回 `{}`。

### 37.10 接口与工具

| 路由 | 方法 | 作用 |
|---|---|---|
| `/receive/files` | GET | 列已落盘 + 带 policy（合并返回，避免页面先空后蹦） |
| `/receive/files/policy` | GET / POST | 看 / 改策略（三键只在真给了时才写） |
| `/receive/files/sweep` | POST | 按策略清一次 |
| `/receive/files/fetch` | POST | 给某条消息补下（`{messageId,index?}`） |

第 18 个工具 `push_hub_files`（`lib/index.js:1879`），action = `list` / `policy` / `setPolicy` / `sweep` / `fetch`。前端 `lib/client.js` 的「入站附件」页（`EXTRA_NAV` 的 `files` 项），三行磁盘策略 `min: 0`、`onChange` 立即 POST，没有保存按钮。

补下是**就地更新**（`inbox.updateAttachments`），不补写新消息 —— 补写会让同一张图出现两次。找不到 id 时回 `{ok:false,detail:'这条消息已经不在收件箱里了'}`，不静默成功。

### 37.11 已知边界

| 边界 | 说明 |
|---|---|
| **只有 6 类能真下** | telegram / slack / discord / matrix / feishu / email。剩下的要看原因：企微智能机器人是链路本身不给；**QQ 与钉钉是平台给接口但本轮没做**（见 37.4 与 38.8）。 |
| **Telegram bot 限 20 MB** | 平台硬限制，与本插件 `maxFileMB` 无关。`file_path` 还会过期，补下时重新 `getFile` 换一次。 |
| **飞书必须要 message_id** | 资源 URL 里带 message_id，所以只能收消息那一刻记下，事后从别处拿不到。 |
| **Matrix 的 allow_redirect 不是所有 homeserver 都支持** | 不支持的会直接回字节（两种都能处理）；既不给字节也不给重定向的会失败并在 detail 里带状态码。 |
| **落盘没有并发保护** | 同一秒两个同名文件后者覆盖前者。发生率极低，等真撞上再加 `-1` 后缀。 |
| **清理不自动跑** | 只在收到新附件时与手动「清一次」两处触发。没有常驻定时器 —— 本插件不该在 DSH 没开时偷偷动硬盘。 |

## 三十八、长连接就绪可见（v0.37.0 新增）

### 38.1 一句话

**飞书连接是通的，界面却永远停在 `starting`** —— 这一版把「我连上了」这件事让 worker 自己说出来，而不是等第一条消息替它说。

### 38.2 缺陷长什么样

v0.36.0 做真实执行验证时撞出来的（不是读代码读出来的）：

```text
POST /receive/start {channel:'feishu'}  → 200 {"ok":true,"started":1}
+4 秒  /receive/status → state:'starting'
+2 分钟 /receive/status → state:'starting'   updatedAt 停在 2026-11-18T15:50:20.633Z
同一时间 telegram → 'running'，wechat → 'running'
```

查 SDK 才发现飞书的连接一直是好的（心跳正常收发）。问题在**状态汇报**：`lib/receiver.js` 里唯一把状态推到 `running` 的地方在 `deliver()` 内部（`appendMessage` 成功之后），而 `deliver()` 只在收到消息时被调。长连接型通道于是永远停在 `starting`。

### 38.3 为什么这在界面上看不出来

`lib/client.js:2493`：

```js
const receivingOf = (channel) => recv.status.some(
  (row) => String(row?.channel) === channel && String(row?.state) !== 'stopped',
)
```

判据只认「是不是 stopped」，所以 `starting` 与 `running` **显示成同一句话**：「正在收 · 已收 0 条 · 时间」。唯一区别是时间戳冻住不动 —— 而这个区别没人会盯着看。结果就是图标写着「正在收」，实际可能根本没连上，要等对方发消息且没反应才发现。

### 38.4 修法：`ctx.onReady` 可选回调

```js
const result = await worker.run(acc, {
  signal,
  onMessage: deliver,
  onReady: () => setStatus(channel, accountName, { state: 'running', received, error: null }),
})
```

三个取舍：

1. **可选不是必需**。`ctx.onReady?.()` 全走可选链，没实现它的 worker（含将来新加的通道）行为与旧版完全一致。做成必需的话，加一个通道就得多写一段样板，迟早有人漏。
2. **`received` 一起写回**。`setStatus` 是合并补丁，只传 `state` 会保留已有 `received`；显式带上是为了返回体永远是完整的一行。
3. **不新增状态名**。没引入 `'connected'` 中间态 —— 前端只认 `stopped` / 非 `stopped`，多一个状态名等于要改前端判据，而用户也不需要知道「连上了但没在收」。

### 38.5 六家的就绪信号从哪来

这一节最要紧的规矩：**就绪信号必须是平台真的给的，不能自己猜一个 `setTimeout(2000)`**。

| 通道 | 就绪信号 | 依据 |
|---|---|---|
| 飞书 | SDK 的 `onReady` | `@larksuiteoapi/node-sdk` 的 `WSClient` 构造函数本来收 `onReady` / `onError` / `onReconnecting` / `onReconnected` |
| Slack | `onSocket(socket, "open", ...)` | undici 的 WebSocket 支持 `addEventListener('open')`；`lib/ws.js:90 onSocket` 已封装 addEventListener / on 两种写法 |
| Discord | 同上 | 同上 |
| QQ | 同上 | 同上 |
| 钉钉 | `client.connect()` 的 `.then()` | `dingtalk-stream@2.1.4` 的 dist 只有 `emit(message.headers.topic, ...)`，**没有就绪事件**；但 `dist/client.mjs:177 async connect() { await this.getEndpoint(); await this._connect() }` —— resolve 即 socket 已 open |
| 企微 | `client.on('connected', ...)` | `@wecom/aibot-node-sdk@1.0.7` 的 `dist/index.cjs.js:940 setupWsEvents()` 里 `this.wsManager.onConnected = () => this.emit('connected')`；另有 `authenticated`，但那是「认证过没过」不是「连没连上」 |

**为什么不用固定延时**：`setTimeout(2000)` 在网快时是「明明连上了还显示 starting」，在网慢时是「明明没连上却显示 running」—— 两头都错且都看不出来。用平台给的事件，唯一失败模式是「事件没来」，而那本来就该显示 `starting`。

### 38.6 每处都包 `try/catch`，理由只有一条

```js
onSocket(socket, "open", () => { try { ctx.onReady?.() } catch { /* 只是展示 */ } })
```

**状态只是展示，绝不能因为一个展示回调抛错就把连接断掉**。不包 try 的话，`setStatus` 内部任何一次意外都会顺着回调栈冒到 socket 的事件处理器里 —— Node 里事件处理器抛未捕获异常是进程级事故。为「时间戳准不准」赔上「一条消息都收不到」，完全不值。

### 38.7 两条验证路线

**结构层**（六个通道全验，靠探针）：`scaffold/probe_download.mjs` K 段 10 项（96 → 106）。钉的是契约不是连接 —— 模拟连接验不出「信号是不是真的平台给的」，而钉契约能保证：只要平台真发了那个事件，状态就会被更新。

**行为层**（只有飞书有账号）：

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:3082/@duma520/dsh-push-hub/api/receive/start' `
  -Method Post -ContentType 'application/json' -Body '{"channel":"feishu"}'
Start-Sleep -Seconds 30
(Invoke-RestMethod -Uri 'http://127.0.0.1:3082/@duma520/dsh-push-hub/api/receive/status').status `
  | Where-Object { $_.channel -eq 'feishu' } | Format-List
```

判据刻意选「**没收到任何消息的情况下时间戳会不会动**」：旧版行为正是「收到第一条才 running」，如果只在发消息之后才变，说明根本没改到点上。

### 38.8 顺带改准的措辞：QQ 与钉钉不是「平台不给」

| 通道 | 平台给什么 | 真实状态 | 现在的文案 |
|---|---|---|---|
| QQ | `getFile` 接口，只有 5 分钟窗口 | 能写，本轮没做 | 「…要在 5 分钟内主动调接口拉 —— 这条本轮没做，所以取不到」 |
| 钉钉 | `downloadCode` 换一次性临时 URL | 能写，本轮没做 | 「…要先用 downloadCode 换一个几分钟就失效的临时 URL —— 这条本轮没做，所以取不到」 |
| 企微（智能机器人） | 回调里没有 `media_id` | 链路本身不给 | 「…这条链路本身就不给原图」 |

**为什么较这个真**：这不是修辞问题，是给用户的信息不同。「平台不给」= 换通道吧，这里永远没戏；「本轮没做」= 催作者还能有。把后者写成前者，等于替用户提前放弃一个做得到的选项。反过来也不能写「暂不支持」—— 那是敷衍，没说清到底谁的问题。

### 38.9 已知边界

| 边界 | 说明 |
|---|---|
| **六家只验了一家** | Slack / Discord / QQ / 钉钉 / 企微 账号数全是 0，六处埋点靠探针钉契约，真连一次没做过。 |
| **就绪 ≠ 健康** | `running` 只说明「连上过一次」。之后 socket 断了会走 worker 自己的重连循环，状态可能停在 `running` 而实际在重连 —— 断连时 `runLoop` 的 catch 会写 `error`，界面能看到，但不会自动退回 `starting`。要做成健康度得引入心跳，另一个量级。 |
| **飞书 onReady 与真能收之间还有一步** | onReady 表示长连接建好，理论上之后立刻能收；若 SDK 内部还有鉴权/订阅，那段时间状态是 `running` 但消息可能还没开始来。 |
| **轮询型不受影响** | telegram / wechat / matrix / email 本来就能在拉取成功时说话，没有这个问题。 |

## 三十九、入站去重与接收游标（v0.38.0 新增）

### 39.1 这一节管什么

管「同一条消息被记了两遍」和「重启一次就把历史全拉一遍」这两件事。它们看着像两个 bug，实际是**一个根的两个枝**，必须一起修，分开修都修不干净。

### 39.2 症状与现场

主人从手机发了一条「你好」，收件箱回了两条：

```
id: telegram-mwmbzp3k-f4oa7i   at: 2026-11-18T16:24:02.000Z  from: 6317****92  text: 你好
id: telegram-mwmbzp3k-8zctwi   at: 2026-11-18T16:24:02.000Z  from: 6317****92  text: 你好
```

同一个时刻，`/receive/status` 里 telegram 掉进了 `retrying`：

```
getUpdates 失败 HTTP 409: Conflict: terminated by other getUpdates request; make sure that only one bot instance is running
```

### 39.3 枝一：重复写入（写入侧毫无抵抗）

`lib/inbox.js` 的 `appendMessage` 原本没有任何去重，id 是这样拼的：

```js
id: channel + '-' + Date.parse(at).toString(36) + '-' + Math.random().toString(36).slice(2, 8)
```

`Math.random()` 意味着同一条平台消息重投一次就**必然**得到两个不同 id。写入侧不是「偶尔漏判」，是**根本没有判的地方**。

### 39.4 枝二：游标没落地（重投完全合规）

Telegram 的 offset 只存在内存 `acc.__offset`。进程一重启就回 0，而 0 在它的语义里是「把还没确认的全部再发一遍」。平台按规矩行事，没有任何过错。

所以「重启一次 → 平台重投 → 收件箱多一份」是一条**必然链路**，不是偶发。这也解释了为什么它一直没被发现：平时不重启就看不见。

### 39.5 根：为什么 409 会掺进来

`startChannel` 的互斥只看内存 Set（`if (set.has(accountName)) continue`）。插件热重载后，**旧模块的接收循环还活着** —— 它跑在旧模块的闭包里，看的是旧 Map；新模块这边 Map 是空的，于是又起一个。两个循环同时 `getUpdates`，Telegram 只允许一个，互相踢，于是 `running` / `retrying` 反复抖。

### 39.6 三条修法

| 修法 | 落在哪 | 一句话 |
|---|---|---|
| 平台唯一键去重 | `lib/inbox.js` `appendMessage` | 键是**通道 + 账号 + 平台唯一键**三合一 |
| 游标落盘 | 新建 `lib/offsets.js` + `receiver.js` | 内存优先、盘上兜底，每轮写回 |
| 接收权抢占 | `lib/offsets.js` + `receiver.js` | 后启动的赢，先启动的安静退场 |

### 39.7 判重键为什么是三个而不是一个

| 只用 | 会怎样 |
|---|---|
| 正文 text | **最坏的一种**。同一人连发两条「你好」是两条真消息，按正文判重会把第二条吞掉 —— 用户以为对方没发，比重复记录难查得多 |
| 平台 id | 两家平台的 id 空间互不相干，telegram 的 `update_id=1` 与 QQ 的 `id=1` 会互相顶掉 |
| 平台 id + 通道 | 同一个机器人被转发到多个群、或多个 bot 收到同 id 消息时仍会误判 |

三合一才够。命中判重时返回 **`ok: true` + `duplicate: true`**，不是 `ok:false` —— 东西确实在箱里，回失败会让调用方以为写崩了去重试，反而放大问题。没有唯一键的（微信 iLink）照旧写入，**宁可偶发重复也不并掉真消息**。

| 企微 | `frame.body.msgid` | 1440 |
| 微信 | **无**（iLink 不给稳定 id） | 373 附近，按设计不补 |

**Telegram 为什么用 `update_id` 不用 `message_id`**：`update_id` 是每一次投递的序号，重投时不变，且同时覆盖消息与回调两种 update；`message_id` 只覆盖消息。它在原代码里本来就取到了（推进 offset 用），不额外取。

### 39.9 老记录的认领（升级自身的坑）

`platformId` 是 v0.38.0 才有的字段。v0.37.0 及以前的 `inbox.json` 里，每条记录**都没有这个键**。升级后第一次重启，Telegram 按游标 0 把未确认的历史重投一遍，精确判重一条都命中不了 —— **历史全体重复一遍**，比原来的 bug 更难看。用户升级完看到收件箱翻倍，会直接判定这版更糟。

所以精确判重 miss 之后还要再走一步：找一条「通道 + 账号相同、没有 `platformId`、且 `at` / `from` / `text` 全同」的老记录，命中就**把键补进那条老记录**（不是新写一条），回 `{ duplicate: true, adopted: true }`。

| 约束 | 缺了会怎样 |
|---|---|
| 只在 `platformId` 为空的老记录上认领 | 认领过一次的记录还带键，会来回改写、每轮都写盘一次 |
| 只在新消息带键时才走这条路 | 微信这种没有唯一键的通道会开始按正文合并，把两条真消息并成一条 |
| `at` 必须严格相同 | 同一句话隔十分钟再发是**新消息**，会被认领吞掉 |

探针 G 段六项钉的就是这些。

### 39.10 已知边界

| 边界 | 说明 |
|---|---|
| **真实重投没验过** | 去重与游标是探针钉的契约；复现 409 要真重载插件再发消息，本轮只做到「代码路径与断言齐全」 |
| **只覆盖 Telegram 游标** | 微信 iLink 的 `get_updates_buf` 同样只在内存，重投行为没验过，动它是盲改 |
| **接收权是插件级不是账号级** | 两个不同 Bot Token 各跑一个循环其实合法（平台限制的是同一 token 只能一个轮询者），现在第二个实例会让第一个退场，两实例共用一份 config 会少收 |
| **群晖无去重** | 它不支持接收，无需处理 |
| **409 的真实来源在插件之外** | 干净重启仍稳定复现 `Conflict: terminated by other getUpdates request`，而插件自身已被接收权压在单实例内、stop 后状态不再动 —— 说明还有一个插件之外的轮询者在抢同一个 Bot Token。插件能做的是「自己不起第二个」，做不了「别人不抢」。查证想用直连排除也被网络挡住（直连 `api.telegram.org` 直接 `ERR fetch failed`，插件走 `proxy` 里的代理） |

> **v0.39.0 更正**：本节当时把来源猜成「本机残留进程或另一份实例」，**猜错了**。插件停着的时候宿主到代理的连接恒为 0 条，本机 8 个 node 进程没有一个在轮询 Telegram；`getWebhookInfo` 的 `url` 是空串。真正决定性的是 Bot API 的 `close`：踢掉后立刻 `HTTP 500`，紧接着又回到 409 —— 那是一个**会自己重连的持久轮询者**，不在本机。详见第四十节。

## 四十、抢不到接收权也不再哑火（v0.39.0 新增）

### 40.1 一句话

409 的来源在插件之外，插件治不了；但**抢不到的时候不能哑火** —— 请求要能被真的停掉，退避要按秒而不是按分钟，停了再开不能自己撞自己，界面上要能看出是「抢不到」而不是「没人发消息」。

### 40.2 上一版的结论为什么错了

v0.38.0 把 409 归因于「热重载后旧模块的接收循环还活着」。这个解释很顺，但有一个可证伪的点：如果真是本机第二个轮询者，那么**插件停掉之后，本机到代理就不该再有那条连接**。

实测：stop 之后采样 8 次 × 7 秒，宿主进程（pid 61248）到 `192.0.2.10:20808` 的连接数**恒为 0**。这一条就把「本机有第二个循环」判死了。

再把本机所有 node 进程逐个看过（8 个：memory-eternal 两个、billion-context 一个、chrome-devtools-mcp 三个、cloudbase-mcp 两个），没有一个跟 Telegram 有关；`Telegram.exe` 是桌面客户端，走 MTProto，不是 Bot API。`getWebhookInfo` 的 `url` 是空串、`pending_update_count` 是 0 —— 也没有 webhook 在抢。

### 40.3 决定性的一枪：`close` 把人踢掉，它立刻回来

Bot API 有一个 `close` 方法。它的正常用途是配合迁移停掉轮询；在这里正好可以当探测器：

1. 先确认平台此刻空闲：`getUpdates{timeout:0, offset:-1}` → `200 / ok:true / result:[]`。
2. `POST https://api.telegram.org/bot<token>/close` → `{"ok":true,"result":true}`。
3. 立刻连发 5 次 `getUpdates{timeout:10}`。

结果：**#1、#2 立刻回 `HTTP 500 Internal Server Error`**（1.3s / 1.2s），**#3、#4、#5 又回到 409**（4.5s / 6.5s / 11.0s）。

500 说明确实有一条轮询被踢掉了（否则平台不会在处理层出错）；紧接着又出 409，说明**它几百毫秒内就重连回来了**。这一下把「本机残留」和「另一份实例」两个假设都排掉了。

### 40.4 旁证：冲突零星，但窗口越长越容易撞

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| 单次时长相关性 | `timeout` 取 2 / 6 / 10 / 16 / 25 秒 | 2 秒的短轮询照样 409，25 秒的也能跑满 → **与自身时长无关** |
| 并发语义 | A 先发、2 秒后 B 再发 | **A 和 B 双双 409** → 不是「后来者踢前者」，是双方都判冲突 |
| 无自我并发 | 30 次 `timeout:0`，每次 await 完才发下一次 | OK=29 / 409=1（**3.3%**）→ 零星，不是必然 |
| 窗口长度 | 3s × 12、8s × 12、25s × 6 | 1/12、3/12、**3/6** → **窗口越长冲突率越高** |

最后一条是关键：窗口越长，两条轮询**重叠**的时间段就越长，撞上的概率自然越高。这正是「两个轮询者在抢同一个 token」的形态，也直接推出了本版的第一条改动 —— 窗口从 25 秒缩到 10 秒。

### 40.5 为什么 `abort()` 以前根本停不掉请求

`stopChannel` 以前只做 `controller.abort()`。但 `lib/http.js` 的 `request()` 从来不看这个 signal —— 它没有 `signal` 参数。所以 abort 只是把布尔量设成 true，**在飞的那条请求一个字节都没被打断**，会一直挂到 `timeoutMs`（`(25+15) * 1000 = 40 秒`）。

于是「停止 → 立刻开始」的真实时序是：新循环发 `getUpdates` 时，旧的那条还在平台上挂着，Telegram 判定两个轮询者 → 409。这不是巧合，是必然。

修法分两条路，因为直连与代理的取消机制不一样：

| 路径 | 取消方式 | 为什么要这样 |
| --- | --- | --- |
| 直连（`direct`） | 把外层 signal 汇进 fetch 自己的 `AbortController` | fetch 只认一个 signal，超时与上层取消必须汇到同一个 controller |
| 代理（`viaProxy`） | 在 abort 时 **`connection.destroy()`** | **只让 Promise 提前 resolve 是不够的** —— Promise 结束了、隧道还开着，平台侧那条 `getUpdates` 仍在跑，下次 start 照样撞 |

第二条是本版最容易写错的地方。一个「看起来能用」的写法是在 abort 时直接 `finish({status:null, body:'AbortError'})`，调用方立刻拿到结果、循环立刻退出、界面立刻变 `stopped` —— 一切都对，除了平台上那条请求还在。然后用户点「开始接收」，409。

### 40.6 为什么 409 要用独立短退避

普通失败（网络断、平台 5xx）用指数退避到 60 秒是对的：那是真故障，退得越久越省事。409 完全不是这类 —— 对方的轮询者随时可能退出，我们退 60 秒等于「一撞就哑火半分钟」，而真正的机会窗口在几秒内。

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `CONFLICT_BACKOFF_MS` | 1500 | 首次重试 1.5 秒，够平台上那条请求结算 |
| `CONFLICT_BACKOFF_MAX_MS` | 6000 | 连续撞的上限，不退化成高频轰炸 |
| 抢回来后 | `conflictBackoff = 0` | 机会随时会再来，不能累积成「越撞越慢」 |

另外 409 **不涨**手上的普通 `backoff`。两者混用会出现这种糟糕情况：一次无关的冲突把普通退避推到 60 秒，之后真遇到网络故障就变成「一次冲突 + 一次断网 = 哑火一分钟」。

### 40.7 启停为什么必须 async

`stopChannel` 以前是同步函数，`return` 的那一刻只代表「我已经调了 abort」，不代表「循环已经退出」。`startChannel` 的互斥又只看内存 Set —— 而 `set.delete(accountName)` 在旧循环的 `.finally` 里，`.finally` 要等循环真正结束才跑。

| 改动 | 旧行为 | 新行为 |
| --- | --- | --- |
| `stopChannel` | 同步返回，循环还在跑 | async，等所有循环 settle 才返回；超时 5 秒后如实回 `drained:false` |
| `startChannel` | 同步返回，`set.has` 就 `continue` | async，先 `await claimOwner`，再 abort 同账号旧 controller 并等它收尾 |
| `LOOP_DONE` | 无 | 新增：键是 `通道/账号`，值是 runLoop 的完成 Promise，stop 靠它知道该等谁 |
| `.finally` | 无脑 `set.delete` | 只删自己那条登记（`if (LOOP_DONE.get(key) === done)`），否则会把新循环的登记抹掉 |

### 40.8 界面为什么也必须改

这条容易被当成「顺手优化」，其实不做的话这版等于没做。旧文案的判断依据是「循环还活着」，所以只要循环在跑（哪怕一直在 409 里打转）就写「正在收 · 已收 0 条」。用户看到这个文案的正确理解是「插件在正常工作，只是没人发消息」—— **而真相是接收权被别人占着，一条都收不到**。两种情况该做的事完全不同。

| 状态 | 文案 | 样式 |
| --- | --- | --- |
| 未开启 | `未开启 · <接收方式>` | 灰（muted） |
| 循环在跑但 `state === 'retrying'` | `正在抢回接收权 · 同一个机器人已被别的轮询者占用 N 次` | 黄（warn） |
| 正常在收 | `正在收 · 已收 N 条`（抢回过就补 `· 抢回 N 次`） | 默认 |

### 40.9 与其他通道的关系

`signal` 是 `lib/http.js` 的通用能力，任何走 `postJson` / `getJson` 的调用都能用。但**目前只有 telegram 的 `poll` 真的接了 `ctx.signal`** —— 飞书 / Slack / Discord / Matrix / QQ / 钉钉 / 企微走的是 `run()`（长连接），它们的关闭靠的是各自的 socket 与 SDK，本轮没有改。

这不是遗漏而是范围控制：长连接的「停」本来就是 socket close，不存在「请求还挂在平台上」这类问题；轮询型里只有 telegram 在本机实测过撞车。微信 iLink 也是轮询型，但它是长轮询式拉取且没有可复现的冲突现象，本轮没动（动了也没法验）。

### 40.10 已知边界（这版之后仍然成立的）

| 边界 | 说明 | 能不能修 |
| --- | --- | --- |
| **409 的来源在插件之外** | `close` 实验已证明那是一个会立刻重连的外部轮询者 | 插件侧到此为止 |
| **缩窗口只能降低概率** | 3 秒窗口实测仍有 3/19 冲突（成功率 78.9%），不是 100% | 不能消除，只能降 |
| **外部轮询者是谁仍未知** | 已排除：本机残留进程、dsh-im（未加载、无同 token）、webhook（url 空）、Telegram 桌面客户端（走 MTProto） | 需用户侧排查是否有别的设备/机器在用同一个 Bot Token |
| **其他通道的取消没验证** | `signal` 是通用能力，但只有 telegram 的 `poll` 接了 `ctx.signal` | 下一版可按需扩 |
| **`drained:false` 的含义** | 5 秒内没退完只是「没等完」，不代表失败 | 属如实报告，不是缺陷 |
| **撞了会抢回来，但撞不撞不由插件决定** | 真机实测：t=6s 冲突 → t=36s 自己回到 `running`；停完立刻开不再自撞 | 这是本版的能力边界，写清楚比假装解决更好 |
